# 技术决策记录（ADR）

本文件记录项目已确定的技术决策及其背景，供接手的 AI Agent 快速对齐，避免"失忆"后推翻既有结论。

格式：编号、决策、背景、影响。新决策追加在末尾，已确定的决策不擅自更改——如需变更，先向客户说明理由并取得同意。

---

## D1 — MCP Server 使用官方 Rust SDK（rmcp），仅实现 Streamable HTTP 传输

- **日期**：2026-09-09
- **决策**：
  1. MCP Server 的协议实现使用官方 Rust SDK [`rmcp`](https://github.com/modelcontextprotocol/rust-sdk)，不自行手写 JSON-RPC 协议层。
  2. 传输方式**只实现 Streamable HTTP**，不实现 stdio。
- **背景**：
  - 客户明确要求遵循标准 MCP 规范，且指定使用官方 Rust SDK。
  - 客户不限定具体 MCP 客户端；对于不支持 Streamable HTTP 的客户端，客户接受用第三方转换工具（Streamable HTTP → stdio）接入，因此应用侧无需承担 stdio 的实现与维护成本。
- **影响**：
  - 启用 `rmcp` feature `transport-streamable-http-server`；不使用 `transport-io`。
  - 无需开发 stdio 桥接进程，架构更简单，凭据与连接池天然留在应用进程内。
  - `rmcp` 3.2.0 不含 SSE 传输 feature。若后续需兼容仅支持旧版 HTTP+SSE 的客户端，需单独评估（当前不在范围内）。
  - 协议层跟随官方 SDK 演进，我们只实现工具与业务逻辑，降低规范漂移风险。

## D2 — MCP 端点暴露方式、鉴权与端口策略

- **日期**：2026-09-09
- **决策**：
  1. **监听地址**：默认仅监听 `127.0.0.1`；提供"允许远程连接"开关，开启后监听 `0.0.0.0`。
  2. **鉴权**：应用自动生成随机 Bearer Token，设置页可查看、复制、重置；客户端手动配置该 Token。
  3. **端口策略**：首次安装启动从 `50001` 开始递增寻找可用端口，首个成功端口持久化；下次启动优先使用持久化端口，若被占用则重新从 `50001` 开始递增寻找并再次持久化。
- **背景**：客户不限定 MCP 客户端所在主机，Agent 可能与 GUI 应用不在同一台机器上，因此需要可选的远程访问能力。
- **影响**：
  - 默认监听回环地址，安全默认值；远程连接需用户显式开启。
  - 端口号持久化在本地配置中；端口选择逻辑需处理"持久化端口被占用"与"重新搜索"两种路径。
  - **待决风险（Q30）**：远程模式下的传输安全。仅 Bearer Token 无加密，开启远程连接时应给出安全警告，并评估强制 TLS 与来源 IP 限制。

## D3 — 终端会话模型：常驻会话 + NUL 分帧 + 标记判定

- **日期**：2026-09-09
- **决策**：采用设计文档 [`docs/design/terminal-session.md`](design/terminal-session.md) 中的"方案 C"。
  1. 终端为**常驻 SSH 会话**，保留工作目录与环境变量；**不申请 PTY**。
  2. 命令通过 SSH channel stdin 以 **NUL 字节（`0x00`）分帧**传输，远端用 bash 内建 `read -r -d ''` 读取后 `eval`；**不依赖 base64 或任何外部命令**。
  3. 命令结束由远端脚本自打印的带随机 nonce 的标记行判定，输出边界明确。
  4. 不支持交互式全屏程序；远端需具备 bash，创建终端时探测。
- **背景**：
  - 客户希望 Agent 像人类一样操作终端，需要保留状态（方案 A 体验最好但依赖提示符识别，不可靠；方案 B 无状态但不像终端）。
  - 客户指出 base64 未必安装在目标主机，架构师改用 NUL 分帧（`execve` 参数以 NUL 结尾，命令不可能包含 NUL），彻底消除该依赖。
- **影响**：
  - `vim` / `top` / `less` 等需 PTY 的程序不可用——符合"Agent 不应做交互式操作"的定位。
  - 单条命令卡死时 MVP 只能终止整个会话；精细化 kill 留待二期。
  - 远端 bash 依赖需在创建终端时探测并明确报错。

## D4 — 终端环境变量加载策略

- **日期**：2026-09-09
- **决策**：
  1. 默认以 **登录 shell（`bash -l -c`）** 启动包装脚本，加载 `/etc/profile` 与 `~/.bash_profile`。
  2. 每个主机可选配置**初始化脚本**，用于 nvm / conda 等需显式加载的环境。
  3. 每个主机可切换为**干净模式**（不加载 profile）。
  4. 创建终端时捕获环境快照（PATH / PWD / bash 版本）写入终端元数据。
  5. READY 标记之前的输出一律丢弃。
- **背景**：客户询问是否会加载目标主机环境变量。默认（非登录 shell + `--noprofile --norc`）不会加载用户自定义 PATH，会导致 Agent 找不到 `node`/`conda`/`docker` 等命令，与人类 SSH 登录体验不一致。
- **影响**：以登录 shell 启动可能受 profile 内容影响（欢迎语、耗时脚本），通过"丢弃 READY 前输出"与"可切干净模式"来控制风险。

## D5 — 命令执行时序模型：同步 + 异步双模式

- **日期**：2026-09-09
- **决策**：
  1. 提供三个 MCP 工具：`run_command`（同步）、`run_command_async`（异步）、`get_command_status`（轮询）。
  2. **同步工具超时后降级为异步**：返回 `command_id` + `status=running`，不报错、不中断远端命令。
  3. 同步默认等待 30 秒，上限 50 秒（可配置）。
  4. **同一终端串行**；终端忙时**排队**，队列上限 10 条。
- **背景**：客户提出同步/异步双模式，由 Agent 自行判断耗时选择。架构师评估认为 LLM 对耗时的预判不可靠（`apt-get update`、`npm install`、`docker build` 等耗时依赖网络与负载），若同步超时直接报错，Agent 可能重试导致命令重复执行；故引入"超时降级"使方案正确性不依赖模型判断准确率。
- **影响**：
  - 三个工具共用同一套异步执行引擎，`run_command_async` 等价于等待 0 秒。
  - 状态机：`queued` / `running` / `completed` / `failed` / `broken`。
  - 并行需创建多终端；每主机终端上限（Q11）成为并行能力的实际约束。
  - 输出需设上限并在截断时标注，避免撑爆 MCP 上下文。

## D6 — 数据存储与凭据加密

- **日期**：2026-09-09
- **决策**：
  1. **单文件 SQLite** 存放全部数据（主机、认证信息、终端、命令历史），便于备份与迁移。
  2. **字段级加密**（AES-256-GCM 或 XChaCha20-Poly1305）保护 SSH 密码、私钥、passphrase；元数据与命令历史明文。
  3. **密钥分层降级**：K1 系统钥匙串优先；不可用时显式让用户选择 K2 主密码或 K3 本地密钥文件（遵循 P1 / P2）。
  4. 命令历史**默认不加密**（人类审计与搜索需要）。
- **背景**：客户希望后续做数据备份与同步，单文件 SQLite 迁移成本最低；同时要求敏感字段加密。架构师指出密钥不能与数据库同处（否则加密无效），客户进一步指出 Linux 可能缺少 Secret Service，故采用分层探测 + 显式降级。
- **影响**：
  - 加密主密钥物理分离于数据库文件。
  - 数据库元数据记录 `key_provider`，应用据此选择解密路径。
  - 跨机器恢复需解决密钥迁移（登记为 Q32，二期）。
  - 所选密钥方式失效时提示无法解密并提供恢复路径，不清空数据。

## D7 — 工程原则 P1 / P2

- **日期**：2026-09-09
- **决策**：确立两条工程原则，见 [`docs/design/principles.md`](design/principles.md)。

- **日期**：2026-09-09

  - CI 首发仅 Windows；跨平台构建配置预留但暂不启用。

## D9 — SSH 协议库：russh

- **日期**：2026-09-09
- **决策**：SSH 客户端实现采用 [`russh`](https://github.com/Eugeny/russh)（纯 Rust、Tokio 异步、无 C 依赖）。
- **背景**：候选还有 `ssh2`（libssh2 绑定，成熟但依赖 native 库）。因客户要求跨平台架构，`ssh2` 的 native 依赖会在 Windows 及未来 macOS/Linux 打包时反复带来麻烦；`russh` 与 Tokio 异步运行时契合。
- **影响**：
  - 无 native 依赖，Tauri 跨平台打包更干净。
  - 编码前需核实当前版本对 ProxyJump、keepalive 等特性的支持（Q9 范围内）。
  - 认证实现基于 russh 的 client handler 接口。

## D10 — 主机密钥校验：TOFU

- **日期**：2026-09-09
- **决策**：采用 **TOFU（首次使用即信任）**。首次连接记录主机密钥；后续连接比对，**不一致则阻止连接并红色告警**，需人类显式确认才更新。
- **背景**：备选为严格模式（需手工导入，安全性最高但繁琐）与不校验（有中间人风险，已排除）。TOFU 与 OpenSSH 默认行为一致。
- **影响**：
  - 主机密钥存入本地数据库，随主机记录管理。
  - 人类界面需展示主机密钥指纹，并提供"确认新密钥"入口。
  - MVP 不实现严格模式，但保留策略字段以便二期扩展。

## D11 — SSH 能力范围与 sudo 提权三模式

- **日期**：2026-09-09
- **决策**：
  1. **MVP 含 ProxyJump**；SFTP、端口转发进二期。
  2. **sudo 提权采纳三模式设计并在一期全部实现**：`deny`（默认）/ `ask` / `auto`，每主机可配。
  3. 实现机制：包装脚本定义并 `export -f` 一个 `sudo` 函数，转发到 `command sudo -A`；密码经 askpass 脚本从远端 FIFO 读取，应用通过独立 SSH channel 写入；不落盘、不进环境变量。
  4. `ask` 模式通过系统通知征求同意，拒绝或 60 秒超时关闭 FIFO 使 sudo 失败。
     > **该点第后半句已被实现修正**：实测发现 askpass 以 O_RDWR 持有 FIFO，
     > 关闭写端不产生 EOF；现改为**向 FIFO 写入空行**使认证失败。
     > 行为等价（sudo 失败），详见 [`docs/design/sudo.md`](design/sudo.md) §7.3。
     > 原始决策保留不改，以便追溯当时的判断依据。
  5. fail-closed：未被拦截的 sudo 调用一律失败。
- **背景**：客户提出由用户选择 sudo 密码处理方式；架构师评估后给出透明拦截 + FIFO 投递方案并说明技术难点，客户理解后决定一期全部实现。
- **影响**：
  - sudo 提权从"二期"提升为"一期"，MVP 范围扩大，需覆盖三种模式的测试分支。
  - 需核实远端 sudo 支持 `-A`、允许非交互执行；`Defaults requiretty` 的主机需用户调整。
  - 需接入 Tauri 通知能力实现 `ask` 模式。
  - sudo 密码为凭据，复用 D6 的加密存储，可选复用 SSH 登录密码。

## D12 — SSH 私钥导入方式

- **日期**：2026-09-09
- **决策**：
  1. 导入方式：**文件选择器 + 粘贴文本**。
  2. 支持格式：**OpenSSH 私钥格式与 PEM**；**不支持 PPK**。
  3. **支持 passphrase**，加密存储，连接时用于解锁私钥。
  4. 界面**只显示指纹**与格式，不回显私钥正文。
- **背景**：私钥导入直接影响 UI 表单与凭据存储设计；客户明确排除 PPK（Windows 用户若需转换，需自行用 PuTTYgen 转成 OpenSSH/PEM）。
- **影响**：导入时需做格式探测与友好报错；指纹计算使用 SHA256（与 OpenSSH 一致）。

## D13 — 终端数量配额

- **日期**：2026-09-09
- **决策**：
  1. 配额：**每主机 5 个**、**全局 20 个**，均可在设置中配置。
  2. 超限**拒绝创建**并返回明确错误；**不自动归档**，由 Agent 自行决定。

- **背景**：Q4 确定并行需多终端，需防止 Agent 无限创建拖垮应用或目标主机。
- **影响**：创建终端路径需做两级配额校验；错误信息需引导 Agent 归档不用的终端。

## D14 — 命令历史保留策略

- **日期**：2026-09-09
- **决策**：
  1. **按时间保留**，默认 **30 天**，可配置（1 小时 ~ 永久，单位 小时/天/周/月）。
  2. **不设条数上限**——高危操作历史必须完整保存，不因条数自动删除。
  3. **不支持分钟级保留期**，**不提供"立即清空"按钮**。
  4. **归档终端的历史永久保留**，直到用户手动删除该终端。
  5. 清理在启动时与每 24 小时各执行一次，**仅清理超期的活跃终端历史**，且清理行为需留痕。
- **背景**：客户认为按条数截断会在关键时刻删除证据；团队认同按时间保留更符合审计直觉，并指出按时间保留同样会删除历史（若需永不丢失应选永久保留 + 备份）。客户进一步决定归档终端永久保留、不提供立即清空、磁盘紧张时手动删除归档终端。
- **影响**：
  - 保留期只作用于活跃终端；归档终端历史不参与清理。
  - 设置页需展示数据库体积与上次清理信息；保留期 < 24 小时时告警。
  - 单条输出上限（Q4）是磁盘占用的主要控制手段。

## D15 — 前端技术栈：Vue 3

- **日期**：2026-09-09
- **决策**：前端采用 **Vue 3**（`<script setup>` + Composition API）+ **TypeScript** + **Vite** + **Tailwind CSS** + **shadcn-vue** + **Pinia** + **Vue Router** + **xterm.js** + **lucide-vue-next**。
- **背景**：团队初版建议 React + shadcn/ui；客户表示更熟悉 Vue。架构师评估后建议采纳客户倾向——本项目由客户长期维护，技术栈熟悉度直接降低长期风险；Vue 3 生态对本项目需求完全够用，Tauri 官方支持 Vue 模板，终端渲染 xterm.js 框架无关。
- **影响**：
  - 组件库使用 shadcn-vue（源码可控、可深度定制），不使用 Naive UI / Element Plus。
  - 前端目录结构与编码规范按 Vue 3 生态组织。

## D16 — 应用形态：托盘常驻

- **日期**：2026-09-09
- **决策**：
  1. 关闭窗口 → **最小化到系统托盘**，应用与 MCP Server 持续运行。

## D30 — 远程连接暂不启用 TLS（Q30）

- **日期**：2026-09-10
- **决策**：**暂不支持 TLS**，允许在仅有 Bearer Token 认证的情况下开放远程连接。
- **背景**：客户评估后认为风险可控，理由：
  - 启用远程连接的典型场景是**局域网内主机互联**（公司内网或个人家庭局域网）；
  - 这类网络中中间人攻击与流量嗅探一般不会发生；
  - Bearer Token 已挡住未授权访问，只是传输未加密。
- **影响**：
  - 现有安全措施：Token 鉴权（常量时间比较）+ 默认仅监听回环 + 开启远程时的界面风险告警。
  - **已知残余风险**：开放远程连接后，Token 与命令内容在网络上以明文传输。若在公共网络或不可信局域网中使用，存在被嗅探的可能。
  - 保留为**未来工作**；届时可考虑 TLS、或改为仅监听回环 + SSH 隧道接入。

## D32 — 工具 schema 的可空参数用 `anyOf` 表达，不用数组形式 `type`

- **日期**：2026-09-10
- **决策**：MCP 工具的 `inputSchema` 中，可空参数一律表达为
  `"anyOf": [{...}, {"type": "null"}]`，**不使用** `"type": ["integer", "null"]`；
  并让该 schema 内联展开，避免出现 `$defs` / `$ref`。
- **背景**：客户用 `npx @modelcontextprotocol/inspector` 实测时，`create_terminal`、
  `run_command`、`run_command_async`、`get_command_status`、`list_terminals`
  五个工具被标记 `Schema portability: 0 error(s), 1 warning(s)`，警告字段正是
  各工具的可空参数（`name` / `wait_seconds` / `tail_lines` / `host_id`）。
  - 根因：`schemars` 1.x 默认把 `Option<T>` 生成为 `"type": ["<T>", "null"]`。
    这是合法的 JSON Schema 2020-12，但部分 MCP 客户端只接受 `type` 为**单个字符串**，
    遇到数组会告警、丢弃该约束，个别客户端甚至拒绝整个工具——"能连上但工具用不了"。
  - 该告警只是**兼容性提示**，不是功能故障：我们的 server 与严格客户端都能正确处理。
    但既然有零成本、语义等价的规避方式，就应当规避。
- **影响**：
  - 新增 `Nullable<T>` 包装类型（`#[schemars(with = "Nullable<T>")]`），
    仅参与 schema 生成，不改变 `Option<T>` 字段的序列化与反序列化行为。
  - 字段类型保持 `Option<T>` 且必须同时保留 `#[serde(default)]`，否则会变为必填。
  - 新增回归测试：`tool_schemas_do_not_use_array_type`、`tool_schemas_have_no_refs_or_defs`、
    `optional_params_use_anyof_with_null`、`optional_params_accept_absent_and_null`，
    并在 MCP e2e 中通过真实 HTTP `tools/list` 再次校验。
  - 后续新增带可选参数的工具时，凡 `Option<T>` 字段都需加 `#[schemars(with = "Nullable<T>")]`，
    否则会重新引入告警。

## D33 — 协议标记按 `command_id` 配对；sudo 密码经 stdin 投递

- **日期**：2026-09-10
- **决策**（修复 V5 / V14，源于安全审计）：
  1. 命令帧格式改为 `<command_id>\n<command>`，结束标记回显该 id：
     `__MF_PERCH_END__<nonce>__<command_id>__<rc>__`。**不再使用自增序号**做配对。
  2. sudo 密码改经 SSH channel 的 **stdin** 投递（远端 `cat > fifo`），
     不再把它拼进 heredoc 脚本。
- **背景**：
  - 远端序号是**会话内**自增，应用用的是**数据库历史**序号，两套命名空间。
    `restore_terminal` 重建会话后远端序号重置，此后每条命令的结束标记都对不上，
    `exit_code` 永不置位，该终端**永久卡死**（必然触发，非偶发）。
  - 密码走 heredoc 会被 sshd以 `sh -c '<脚本>'` 执行，密码出现在远端
    `ps` / `/proc/<pid>/cmdline` 中，同机用户可读。
- **影响**：
  - `encode_frame` 签名变为 `encode_frame(command_id, command)`；
    `Session::send_command` 同样需要 command_id。
  - `SessionEvent::CommandFinished` 与 `SessionOutput::Finished` 改为携带 `command_id`；
    `ActiveCommand` 不再保存 `seq`（`seq` 仍写入数据库供人类侧排序展示）。
  - 结束标记不再匹配非当前命令的 id，收到不匹配的标记只记 debug 日志并唤醒等待者，
    不会污染状态。
  - 相关测试与集成测试同步更新。

## D34 — 结束通知改用 `watch`，消除丢失唤醒

- **日期**：2026-09-10
- **决策**（修复 V4）：命令结束通知由 `tokio::sync::Notify` 改为 `watch` 通道
  （封装为 `FinishNotifier`）。
- **背景**：`Notify::notify_waiters()` **不保留许可**。等待侧是"先查状态、再 await"，
  若结束侧在等待者订阅之前完成置位与通知，通知即丢失，等待任务永久阻塞，
  `exec_lock` 永不释放，该终端后续命令全部堆积直至队列上限。
- **影响**：
  - 信号值用单调递增计数，保证每次结束都产生一次可观察变更。
  - 等待顺序固定为"先 `borrow_and_update` 记录代次 → 再查状态 → 最后 `changed()`"，
    任何时序下都不会错过唤醒。
  - 会话注销（归档/删除）时发出 `Disconnected`，避免等待者挂在信号上。
  - `FinishNotifier` 独立成类型，使其可**脱离真实 SSH 会话**做单元测试——
    这正是 V4 过去没被测出的原因。

## D35 — 内部机密（MCP Token）落盘加密，无主密钥时显式降级

- **日期**：2026-09-10
- **决策**（修复 V16）：MCP Bearer Token 不再明文存 `settings` 表。
  有主密钥时以 `enc:v1:...` 加密存储；**无主密钥时以 `plain:v1:...` 显式降级**。
  读取通过 `crypto::decrypt_internal`，同时兼容历史遗留的无前缀明文。
- **背景**：Token 等价于"对所有已配置主机的命令执行权"。此前它与凭据不同，
  以明文存在数据库里；读到库文件即等于拿到执行权。
- **影响**：
  - 采用**显式前缀**而非"能不能加密就加密"的模糊行为，
    降级必须可被观察到（P2：安全降级不得静默）。
  - **不阻断 K2（主密码）未解锁时的 MCP 可用性**：若强制加密，
    未输入主密码时 MCP 将无法启动，破坏既有使用方式。
  - `endpoint::ensure_token` / `regenerate_token` 新增 `key: Option<&[u8; KEY_LEN]>` 参数；
    新增 `existing_token` 用于只读展示（不生成新值）。

## D37 — sudo 应答按索要配对（每次索要一条 FIFO）

- **日期**：2026-09-11
- **决策**（修复 B2）：
  1. **每次 sudo 索要使用一条独立 FIFO**：`sudopw.fifo.<会话 nonce>.<askpass PID>`。
     askpass 在 sudo 执行时自建、读走应答后自删；会话建立时**不再预建** FIFO。
  2. 请求标记改为 `__MF_SUDO_REQUEST__<nonce>__<token>__`，`token` 即 askpass 的 PID；
     应用按 `(nonce, token)` 把应答精确写入对应 FIFO。
  3. 令牌**只接受 1–10 位 ASCII 数字**——它会被拼进应用下发的命令（FIFO 路径），
     非法令牌按普通输出丢弃，不产生索要。
  4. 应用侧写入前加 `test -p` 守卫：目标不是 FIFO 时直接失败（fail-closed），
     而不是让 `cat > path` 创建普通文件把密码写到磁盘。
  5. askpass 增加 `read -t 120` 兜底读超时，shebang 因此改为 `#!/bin/bash`
     （dash 不支持 `read -t`）。
- **背景**：
  - 原设计共用一条**会话级** FIFO。FIFO 上一次写入只会被**其中任意一个**正在
    阻塞的读者取走（POSIX 未规定是哪一个），因此同一会话内两次并发索要时，
    应答会按"用户点击顺序 vs 读者阻塞顺序"错配：用户批准的那次可能拿到空密码
    而失败，**被拒绝的那次可能拿到密码而越权**。
  - 曾评估更小的方案"同一终端只允许一个待决索要"，结论是**不成立**：askpass
    在打印标记前就已持有 FIFO 读端，第二个索要的读者必然先于应用判断存在，
    "拒绝第二个请求"的写入同样会被合法请求偷走。
  - 副产物：setup 不再创建 FIFO，V1（setup 的通配删除把刚建的 FIFO 删掉，
    导致 `cat > fifo` 退化为普通文件、密码明文落盘）的成因在结构上消失。
- **取代关系**：
  - 取代 **D11 第 3 点**中"sudopw.fifo 单条会话级 FIFO"的表述（投递机制改为按索要配对）；
  - 取代 **D11 第 4 点**中"关闭 FIFO 使 sudo 失败"的表述（实际做法是向 FIFO 写空行，
    见 [`docs/design/sudo.md`](design/sudo.md) §7.3）；旧条目保留原文以便追溯。
- **影响**：
  - `ssh::protocol`：`askpass_script`、`sudo_fifo_name(nonce, token)`、
    `is_valid_sudo_token`、`session_setup_script`、`session_cleanup_script`；
    `SessionEvent::SudoRequest` 携带 `token`。
  - `ssh::session`：`send_sudo_password(token, ..)` / `deny_sudo(token)`。
  - 会话清理按 nonce 前缀清扫 FIFO（`-type p`），不影响其它会话。
  - 新增 e2e 回归 `concurrent_sudo_requests_do_not_cross_route`。已验证其在
    "临时降级回共用 FIFO"时**失败**、恢复后通过——满足 P3 对能区分对错实现的要求。
- **相关**：D11（sudo 三模式）、D33（协议标记按 id 配对，同一思路）。
- **已知待办**：sudo 密码错误会重试（默认 3 次），`ask` 模式下用户可能看到多次
  确认；合并为一次询问属体验优化，尚未实施。

## D38 — MCP 会话空闲超时改为 24 小时，不沿用 rmcp 的 5 分钟默认值

- **日期**：2026-09-11
- **决策**：`McpManager` 显式构造 `LocalSessionManager` 并设置
  `session_config.keep_alive = Some(24h)`（常量 `SESSION_IDLE_TIMEOUT`，
  集中在一处便于调整）。
- **背景**（客户实测反馈）：
  - 客户用官方 **MCP Inspector** 手动测试，空闲约 10 分钟后工具调用报
    `Error POSTing to endpoint: Not Found: Session not found`。
  - 根因在 rmcp：`SessionConfig::default().keep_alive` 为 **300 秒**，
    会话 worker 空闲到点后以 `IdleTimeout` 退出、会话被从会话表中移除；
    客户端再带原 `mcp-session-id` 请求即得 `404 Session not found`。
    我们此前直接使用 `LocalSessionManager::default()`，等于接受了这个默认值。
  - 对"人 + Agent 交互使用"的桌面应用，5 分钟太短：用户去开会、Agent 停下来
    思考，回来连接就"断了"。而 MCP Inspector **不会**按规范在收到 404 后自动
    重新 initialize，于是表现为一条刺眼的报错。
- **为什么不设为 `None`（永不过期）**：rmcp 文档提醒，HTTP 连接被静默断开
  （如 HTTP/2 `RST_STREAM`）时无超时会留下僵尸会话。24 小时既覆盖任何
  人机交互间隔，又保留有界兜底。若客户希望彻底不过期，改这一个常量即可。
- **影响**：
  - `src-tauri/src/mcp/server.rs`：新增 `SESSION_IDLE_TIMEOUT` 与
    `session_manager()`；`StreamableHttpService` 不再用 `default()`。
  - 新增单测：rmcp 默认值是 300 秒（记录被绕开的坑）、我们的管理器不继承该默认值、
    超时不得短于 1 小时。
  - 新增 e2e：`expired_session_is_reported_as_not_found`（把超时压到 1 秒，
    秒级复现"会话不存在"，即客户看到的现象）；
    `mcp_session_survives_idle_longer_than_rmcp_default`（生产配置下空闲
    310 秒后同一会话仍可用，`--ignored` 运行）。
- **相关**：D1（rmcp）、D2（端点与鉴权）。
- **说明**：会话过期本身符合 MCP 规范（客户端应据此重新 initialize），
  因此这属于**服务端体验取舍**，不是规范违背。

## D39 — 断开的终端在执行命令时按需自动重连

- **日期**：2026-09-11
- **决策**：
  1. **执行命令前按需重建会话**：`run_command` 发现该终端没有可用会话时，
     若状态为 `broken`（或状态仍是 `active` 但会话已丢），**自动重建** SSH 会话，
     沿用原终端 ID 与命令历史，然后照常执行这条命令。归档终端仍然一律拒绝。
  2. **重建必须显式告知**：结果里带 `session_reconnected: true`，并在该命令输出
     开头写入一条 `[mf-perch]` 审计行——重建后是全新 shell，
     **工作目录、环境变量、后台进程都不再保留**（D3 的"状态保留"不再成立），
     Agent 必须知道要重新 `cd` / `export`，人类也要能审计到。
  3. **不新增 MCP 工具**：没有引入"重连工具"，工具面保持 7 个。
  4. **人类侧同时开放重连**：新增 `reconnect_terminal` IPC 与界面按钮，
     与 Agent 侧走同一条路径（`AppState::ensure_terminal_session`）。
  5. **重连不做配额校验**（与"恢复归档"不同）：`broken` 终端本就算在配额里
     （`count_active` 只排除 `archived`），再校验会把它自己数进去，
     在"刚好占满"时误报配额超限。
- **背景**（客户实测反馈）：
  - 客户重启应用后用 MCP Inspector 测试：`list_terminals` 显示终端 `broken`，
    `run_command` 返回 `terminal_broken`，提示"请重建终端"。
  - 但**重建的手段并不存在**：MCP 工具里没有重连/激活工具，人类界面也没有
    （恢复按钮只在 `archived` 时出现，见 `TerminalDetailView.vue` 的 `canRestore`）；
    Agent 只能 `create_terminal` 另建一个新终端，旧终端则一直占着配额。
    配额统计"未归档即计数"，因此**反复重启几次就会撞满每主机配额**，
    此后连新建都会失败——Agent 会被彻底卡死。
  - 触发条件是**常规路径**而非边缘情况：应用每次启动都会把所有未归档终端
    标记为 `broken`（`state.rs`），即"人类重启一次，Agent 手上终端全部失效"。
  - 评估过"给 Agent 一个显式重连工具"的方案：断开多由**人类重启**或网络引起，
    不是 Agent 的意图；让它先探测状态再决定重连，等于把连接管理泄漏进它的推理，
    而且它手上只有 `terminal_id` 这一个句柄。终端软件（Termius 等）的惯例也是
    自动重连并在面板提示，而不是让你删掉标签页重开。
- **影响**：
  - `terminal/mod.rs`：新增 `has_live_session`、`reconnect_terminal`、
    纯函数 `decide_session_action`（分支可测）、共享的
    `load_connection_context`；`RunOutcome` 增加 `session_reconnected`；
    条目新增 `pending_note`，由重建后的**第一条真正执行的命令**写入输出。
  - `state.rs`：新增 `AppState::ensure_terminal_session`（取密钥 → 判定 → 重建）。
  - `mcp/tools.rs`：`run_command_impl` 先确保会话，再回填 `session_reconnected`；
    更新 `run_command` / `list_terminals` 的工具描述（英文）。
  - `ipc/mod.rs` + `lib.rs`：新增 `reconnect_terminal` 命令；
    前端新增 `reconnectTerminal`、store 的 `reconnect`、
    详情页与列表页的「重连」入口，并修正 broken 提示文案。
  - 新增单测 3 项（活跃会话直接用 / broken 重建 / 归档永不重建）；
    新增 e2e `run_command_auto_reconnects_broken_terminal_after_restart`
    （同一数据库文件开两个 AppState 模拟重启、配额压到 1、走真实 MCP HTTP）。
  - 顺带修正：端口相关单测在端口被占用时**失败并提示如何处置**
    （退出应用 / 等待并发测试结束），不再静默跳过——静默跳过会把
    环境问题伪装成绿色通过。
- **取代/扩展**：扩展 D20（归档恢复）的"沿用原 ID 与历史"语义到 `broken` 场景；
  取代 [`docs/design/terminal-session.md`](design/terminal-session.md) §5 中
  "Agent 需重建"的表述（原文没有可用的重建手段，属能力缺口）。
- **已知待办**：
  - 运行中断线（非重启）目前**不会**把数据库状态落为 `broken`——
    终端看似 `active` 但实际无会话，直到下一次命令触发重连才恢复。
    人类界面在此期间可能显示得偏乐观，后续可让输出泵在断开时落库。
  - 若主机本身不可达，重连会失败并报 `ssh_connect_failed`，状态保持 `broken`，
    Agent 应据错误原因判断而不是反复重试。

## D40 — 落实 D22：终端事件推送，界面跟随 Agent 实时更新

- **日期**：2026-09-11
- **决策**（落实 D22 已承诺的"应用内实时状态更新"）：
  1. 终端运行时发布**领域事件**：`TerminalCreated`、`TerminalRemoved`、
     `CommandStarted`、`CommandFinished`、`SessionChanged`（含状态与人类可读原因）。
  2. 运行时**不依赖 Tauri**：事件经无界 channel 交给外壳层（`lib.rs`）转发为
     单一 Tauri 事件 `terminal://event`（负载带 `kind` 标签）。
     与 `sudo://request` 的注入模式一致，因此运行时可在测试中直接订阅断言。
  3. **尽力而为的投递**：事件只用于"界面新鲜度"，真实状态始终以数据库为准，
     因此不阻塞、不回压、不重试；接收端关闭（应用退出）时静默跳过。
  4. 前端在 store 层订阅，收到事件后**去抖 250ms** 刷新终端列表；
     命令类事件且与当前查看的终端相关时，同时重放最近一次历史查询。
  5. **兜底校准**：窗口重新可见/获得焦点时主动刷新一次——托盘常驻（D16）下
     窗口可能长时间隐藏，事件推送不保证被消费。
  6. 顺带关闭 D39 的已知待办：输出泵检测到断开时**把状态落库为 `broken`**
     （此前只有应用重启才会落），界面与数据库都真实反映断线。
- **背景**（客户实测反馈）：
  - 问题①：Agent 触发自动重连后，审计页仍显示"连接已断开…你也可以点重连"，
    要人工点一次按钮才消失——审核者可能误以为终端仍未恢复。
  - 问题②：Agent 执行的命令不会实时出现在审计页，必须人工点刷新。
  - 两者**同一根因**：前后端之间此前只有 sudo 一条推送通道，其余全靠页面挂载时
    拉取一次。后端数据本身是对的（重连后状态已是 `active`），是界面陈旧。
- **影响**：
  - 新增 `src-tauri/src/terminal/events.rs`（事件枚举、通道、事件名常量）；
    `TerminalRuntime` 增加 `set_event_sink` / `emit`，`TerminalEntry` 共享同一槽位
    （已运行的输出泵也能发事件）；输出泵增加落库 broken。
  - `lib.rs` 装配事件转发；`RunOutcome` 的 `session_reconnected` 语义不变。
  - 前端：`stores/terminals.ts` 增加 `startListening` / `stopListening` /
    `refreshHistory`，`App.vue` 订阅事件并注册焦点校准。
  - 测试：新增单测（归档/删除必须发事件、未注入出口时不得 panic）；
    既有 e2e `run_command_auto_reconnects_broken_terminal_after_restart`
    扩展为同时断言 `session_changed` / `command_started` / `command_finished`。
- **相关**：D22（本次即其落地）、D39（重连）、D16（托盘常驻）、D19/D25（人类是审核者）。
- **不做**：命令完成的**系统通知**仍按 D22 留在二期；命令输出内容不走事件通道
  （界面需要输出时按 `command_id` 走既有 IPC 拉取），避免把大段输出塞进事件。
