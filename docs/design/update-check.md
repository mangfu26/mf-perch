# 更新检查方案设计

> 状态：已确认（Q21 / Q34）；**版本源方案已被 D55 更新**（Gist → 仓库根 `update.json`，
> 由发布流水线随发版自动回写），本文 §2 的 Gist/Releases-API 对比保留为选型历史背景，
> 现行格式规范以 [`docs/update-manifest.md`](../update-manifest.md) 为准。
> **D58**：本文多处提到的"下载页 / Release 页"就是按钮的目标——**该版本的发布页面**，
> 不是安装包直链（§2.4 第 8 点的"不自动打开浏览器"不变）。
> 客户方案：不做自动安装更新；应用从 GitHub Gist 读取版本信息，发现新版本则提示用户去 Release 页下载覆盖安装，并提供"检查更新"按钮。

## 1. 客户方案

- 不做自动更新（A 方案）：用户自行到仓库 Release 页下载新版本覆盖安装。
- 版本信息放在 **GitHub Gist**，应用读取并比对版本。
- 发现新版本 → 提示用户去下载。
- 提供手动"检查更新"按钮。

## 2. 团队评估

### 2.1 方向正确

- **不做自动安装**是合理的：自动更新需要签名密钥、回滚策略、更新包托管，成本高且与 MVP 核心价值无关。
- **"检查版本 + 提示下载"**是低成本、低风险的做法，用户保留最终控制权。
- 手动检查按钮是必要的补充。

### 2.2 对"用 Gist 作为版本源"的评估

| 维度 | Gist | 团队意见 |
| ---- | ---- | ---- |
| 可访问性 | 公开 Gist 有固定 raw URL，无需鉴权 | 可行 |
| 限流 | raw 内容由 CDN 提供，不占 REST API 配额 | 优于 REST API |
| **一致性风险** | **需人工每次发版后手动更新 Gist** | **主要问题** |
| 归属风险 | Gist 属于个人账号，误删/改名则更新检查失效 | 需注意 |
| 与发布流程的关系 | 与 Release 是**两套独立产物**，容易不同步 | 需改进 |

**核心问题：Gist 与 Release 是两套需要人工保持一致的东西。** 发版时忘记更新 Gist，用户就永远收不到更新提示——这类"忘记同步"的故障很隐蔽，且用户侧表现为"检查更新永远说已是最新"。

### 2.3 建议方案：以 GitHub Releases API 为版本源

应用直接请求：

```
GET https://api.github.com/repos/<owner>/<repo>/releases/latest
```

可获得：

- `tag_name` → 版本号（如 `v0.2.0`）
- `body` → 发布说明
- `assets[]` → 安装包下载地址（按平台/后缀筛选）
- `html_url` → Release 页面
- `published_at` → 发布时间

**优势**：

1. **单一数据源，零人工同步**——发版流程本来就要创建 Release，版本信息自动一致，不存在"忘记更新 Gist"的故障。
2. **下载地址、发布说明、版本号天然齐全**，不需要额外维护文件。
3. 无鉴权即可读取公开仓库。

**代价**：走 REST API 有**未认证限流（60 次/小时/IP）**。对"每次启动检查一次 + 手动检查"的频率完全够用，但必须配合下面的缓存策略。

### 2.4 无论用哪种源，都必须满足的设计要求

1. **异步、非阻塞**：更新检查在后台进行，不阻塞启动、不影响 MCP Server 与终端功能；网络失败**静默忽略**，不弹错误打扰用户。
2. **超时与重试**：请求超时 5 秒；失败不重试（下次启动再试）。
3. **结果缓存**：检查结果缓存，**默认每 24 小时最多检查一次**；手动按钮不受缓存限制（但做最小间隔防连点）。
   缓存**按应用版本作废**：缓存里记着它是为哪个版本算出来的，当前版本与之不符时一律当无缓存重查。
   否则升级后 24 小时内会沿用升级前的结论——0.1.0 时缓存的"有 0.1.1 可更新"会在用户已经装上
   0.1.1 之后继续提示"发现新版本 0.1.1"。
4. **语义化版本比对**：使用 semver 比对；**应用版本高于远端时不提示**（避免开发版被"降级"提示）。
5. **每个版本只提醒一次**：用户点"忽略此版本"后不再重复提示，直到出现更新的版本。
6. **可配置更新源**：更新源 URL 可在设置中修改。理由：
   - GitHub 在某些网络环境下可能不可达，用户可指向镜像或自建地址；
   - 你未来若换发布方式（Gist / 自建 JSON），无需改代码。
   - 这实际上让"Gist 方案"成为**可选的替代源**，而不是唯一方案。
7. **隐私与可关闭**：自动检查会向 GitHub 暴露 IP 与"该用户在用此应用"。默认开启，但**设置页提供关闭开关**，并在文档中说明。
8. **不自动打开浏览器**：仅提示；用户点击按钮才打开下载页（避免意外弹窗）。
9. **安装包校验信息**：Release 说明中提供安装包的 **SHA256**，用户下载后可自行校验。我们不做自动安装，但可以帮用户确认下载完整性。
10. **覆盖安装的用户数据**：安装新版本覆盖旧版本时，`%APPDATA%/mf-perch` 下的数据与凭据保留，不会被清除（需在发版测试中验证）。

## 3. 建议的元数据结构（若采用"可配置 JSON 源"）

```json
{
  "version": "0.2.0",
  "notes": "本次更新内容…",
  "pub_date": "2026-09-10T10:00:00Z",
  "platforms": {
    "windows-x86_64": {
      "url": "https://github.com/.../mf-perch_0.2.0_x64_en-US.msi",
      "sha256": "…",
      "size": 12345678
    }
  }
}
```

- Releases API 模式下由应用从 Release 数据**映射**为上述结构，前端只认这一种结构，便于将来切换源。
- Gist / 自建源模式下则直接读取该 JSON。

## 4. MVP 范围界定

| 能力 | 一期 |
| ---- | ---- |
| 启动后自动检查更新（后台、静默失败、24h 缓存） | ✅ |
| 设置页"检查更新"手动按钮 | ✅ |
| 发现新版本 → 应用内提示 + 跳转下载页 | ✅ |
| "忽略此版本" | ✅ |
| 更新源可配置 | ✅ |
| 自动下载 / 自动安装 / 静默升级 | ❌ 二期及以后 |

## 5. 已确认结论（Q21 / Q34，2026-09-10）

- 客户答复：**接受 Gist 方案的同步风险**，采用 **Gist 作为版本信息源**。
- 客户说明的发布流程（与 Gist 更新时机绑定）：

  1. 客户指示团队给 `main` 打 tag（或客户手动打）；
  2. 推送到 GitHub；
  3. GitHub Actions 检测到 tag → 构建产物 → **发布一个 Release 草稿**；是否发布由客户决定；
  4. **客户手动更新 Gist**（版本信息）。

- 结论：
  - 版本源：**Gist 中托管的版本信息文件**（JSON，结构见第 3 节）。
  - 应用启动后台检查 + 设置页手动检查按钮；发现新版本提示并提供下载跳转。
  - **更新源 URL 仍做成可配置**：默认指向该 Gist，若 Gist 不可用或将来更换方式，用户可自行改地址，无需改代码。
  - 其余设计要求（异步静默失败、24h 缓存、semver 比对、忽略此版本、可关闭、不自动打开浏览器、显示 SHA256）照第 2.4 节执行。
  - **不做自动下载与自动安装**（二期及以后）。

### 5.1 团队补充提示

- Gist 应在 **Release 正式发布之后**再更新，否则用户会被引导到一个尚未发布的页面。
- 建议 Gist 内容包含：`version`、`notes`、`pub_date`、各平台 `url` + `sha256`。
- 若将来 Gist 方案维护吃力，可平滑切到 Releases API 或自建 JSON——因为源地址可配置、前端只认统一结构。

## 6. 版本发布流程（团队必须遵守）

> 与 `AGENTS.md` 的 git 规范一致：**tag 只能由客户明确指示时创建与推送**。

```
① 客户明确指示"发布 vX.Y.Z"
   ↓
② 团队将 develop/xxx 合并到 main（需客户确认合并方式，见 AGENTS.md 1.4）
   ↓
③ 同步所有版本号来源使其一致
   （package.json / src-tauri/tauri.conf.json / 更新清单）
   ↓
④ 创建 tag：git tag vX.Y.Z（仅在客户指示后）
   ↓
⑤ 推送 tag 到 GitHub（仅在客户指示后）
   ↓
⑥ GitHub Actions 检测到 tag → 构建产物 → 创建 Release 草稿
   ↓
⑦ 客户决定是否发布该 Release
   ↓
⑧ 客户手动更新 Gist 中的版本信息
   ↓
⑨ 旧版本应用检查到新版本 → 提示用户下载覆盖安装
```

**红线**：

- 团队**不得**在客户未明确指示时创建或推送 tag。
- 团队**不得**自动合并到 `main`（见 AGENTS.md 1.4）。
- 自动更新所需的签名密钥（若二期启用）**绝不能提交到仓库**。
