# 工程设计原则

本文件记录团队在本项目中确立的工程原则。这些原则来自与客户沟通中暴露的真实问题，用于指导后续所有设计决策，避免重复犯错。

---

## P1 — 不假设运行环境存在外部依赖

**原则：任何对"目标主机"或"用户运行环境"的依赖，都必须显式探测、优雅降级、明确报错，不得静默假设其存在。**

**来源**：本项目已两次因"假设环境存在某组件"而调整设计：

1. **终端命令传输**：最初设计用 `base64` 编解码命令，客户指出"不能保证目标服务器装了 base64"。改为 NUL 字节分帧 + bash 内建 `read -d`，彻底消除外部命令依赖。
2. **加密密钥存储**：初版建议用系统钥匙串（OS keyring），客户指出"Linux 下如果没有安装密钥服务怎么办"。改为分层探测 + 显式降级方案。

**落地要求**：

- **探测优先**：使用任何外部能力前，先探测其可用性（如 `command -v bash`、keyring 可用性检查）。
- **优雅降级**：探测失败时提供明确的替代路径，而不是让功能静默失效。
- **明确报错**：无法降级时，返回清晰的错误原因与用户可操作的建议，不返回模糊的"操作失败"。
- **禁止静默降级**：涉及安全语义的降级（如密钥保护强度下降）必须告知用户并取得同意。
- **优先内建/标准能力**：能用语言或平台内建能力解决的，不引入外部命令或第三方服务。

**适用范围**：SSH 目标主机环境、用户操作系统环境、依赖的外部工具与系统服务。

---

## P2 — 安全降级必须显式告知

**原则：当安全强度因环境限制而下降时，必须在界面上明确告知用户风险，并让用户主动确认，不得悄悄降级。**

**来源**：密钥存储的降级路径（如从系统钥匙串降级到本地密钥文件）会降低安全强度。若静默降级，用户会在不知情的情况下以更低安全性运行。

**落地要求**：

- 界面明确展示当前使用的保护方式（钥匙串 / 主密码 / 本地密钥文件）。
- 降级时给出风险说明与推荐选项。
- 记录到应用日志（不含敏感内容），便于审计。

## P3 — 安全属性必须有"能区分对错"的测试，不能依赖功能测试

**原则：涉及安全属性的实现，必须构造**能区分正确实现与错误实现**的断言；
"操作成功"类的功能断言不足以证明安全属性成立。**

**来源**：2026-09-10 的全量安全审计（[`security-audit.md`](../security-audit.md)）
发现一个曾被测试绿灯掩盖的严重缺陷：

- sudo 密码注入本应经 **FIFO** 在内存中传递、不落盘。但因 setup 脚本先建 FIFO、
  后执行通配删除，把刚建好的 FIFO 自己删掉了；后续写入退化为"创建普通文件"，
  **密码以明文落在远端磁盘且同机可读**。
- 而当时的 e2e 测试**照常通过**——因为它断言的是"sudo 成功了吗"，
  而普通文件同样支持写读。功能上完全正常，安全上完全失效。
- 团队的"修复前先还原缺陷、确认测试会失败"的差分验证，
  才真正证明了新测试有效（还原旧写法 → 测试失败；修复后 → 通过）。

**落地要求**：

- **识别安全属性**：凡是"不落盘 / 不泄露 / 不可绕过 / 不可伪造 / 权限边界"一类的目标，
  都属于安全属性，不能只靠功能测试。
- **断言要触及本质**：直接检查载体本身（如文件类型是 FIFO 还是普通文件、
  返回结构中是否含敏感字段、越权请求是否被拒绝），而不是只检查"操作返回成功"。
- **做差分验证**：修复安全缺陷后，临时还原错误实现，确认测试**确实会失败**；
  否则无法排除"测试对这类错误不敏感"。
- **诚实标注残余风险**：无法根治的要显式写明"已缓解但未消除"，
  不得用"已修复"掩盖。典型例子见 `security-audit.md` 中的 V2
  （协议标记可被读取与伪造，需协议层改造才能根治）。

**教训一句话**：**功能测试通过 ≠ 安全属性成立。**
