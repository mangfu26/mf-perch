# 前端技术栈设计

> 状态：已确认（Q13）
> 客户倾向：更熟悉 Vue，希望切换到 Vue 3。

## 1. 候选方案对比

| 维度 | React + shadcn/ui | **Vue 3 + shadcn-vue（建议）** | Svelte |
| ---- | ---- | ---- | ---- |
| 客户熟悉度 | 低 | **高** | 低 |
| 生态成熟度 | 最高 | 高（仅次于 React） | 中 |
| Tauri 官方模板支持 | 有 | **有** | 有 |
| 组件库可定制性 | shadcn 源码可控 | **shadcn-vue 源码可控**（基于 reka-ui） | 需自建较多 |
| AI 辅助编码资料 | 最多 | 多 | 较少 |
| 长期维护成本 | 低 | **低**（客户熟悉，可直接维护） | 中 |

**结论：采纳客户倾向，使用 Vue 3。**

理由：

1. **客户熟悉度是决定性因素**。本项目由客户长期维护，技术栈若客户不熟悉，日常排障、审阅与二次开发都会付出额外成本；客户对 Vue 的熟悉度直接降低项目长期风险。
2. Vue 3 生态对本项目需求完全够用：Tauri 官方支持 Vue 模板；表单、表格、虚拟滚动等均有成熟方案。
3. AI 辅助编码方面，Vue 3 + TS + `<script setup>` 的训练资料同样充足，差距不影响交付。

## 2. 建议技术栈

| 层 | 选型 | 说明 |
| ---- | ---- | ---- |
| 框架 | **Vue 3** | 使用 `<script setup>` + Composition API |
| 语言 | **TypeScript** | 严格模式，前后端契约类型化 |
| 构建 | **Vite** | Tauri 官方模板默认，热更新快 |
| 样式 | **Tailwind CSS** | 便于实现深色主题与终端类界面 |
| 组件库 | **shadcn-vue** | 源码复制进项目、完全可控，基于 reka-ui（原 radix-vue） |
| 终端渲染 | **未采用**（不使用 xterm.js） | 人类侧是**审计视图**，命令输出用 `<pre>` 等宽渲染即可（`src/views/TerminalDetailView.vue`）。`@xterm/xterm` 目前只在 `package.json` 里声明、**全仓库零 import**（2026-09-16 核对）；二期若真需要终端渲染（光标控制、TUI 类输出）再评估引入——它框架无关，接入成本低 |
| 国际化 | **vue-i18n** | 界面文案统一走 `src/i18n/locales/zh-CN.ts`（当前仅中文一种），不在组件里写死中文 |
| 状态管理 | **Pinia** | Vue 官方推荐 |
| 路由 | **Vue Router** | 多页面（主机 / 认证 / 终端 / 设置） |
| 图标 | **lucide-vue-next** | 与 shadcn-vue 配套 |

### 2.1 关于组件库的备选

| 方案 | 优点 | 缺点 |
| ---- | ---- | ---- |
| **shadcn-vue（建议）** | 源码可控、可深度定制、无版本绑架 | 需自行组装，初始工作量略高 |
| Naive UI | 开箱即用、组件全、TS 友好 | 定制需覆盖样式，深度改造受限 |
| Element Plus | 生态成熟、中文文档好 | 视觉偏管理后台，终端工具感较弱 |

**建议 shadcn-vue**：本项目需要"类 Termius 的专业深色界面"，深度定制需求强，源码可控比开箱即用更重要。
