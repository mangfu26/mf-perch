# 命令执行时序模型设计

> 状态：已确认（Q4）
> 本文评估客户提出的"同步 + 异步双模式"方案，并给出团队建议。

## 1. 客户方案

- **同步**：执行命令并等待完成，直接返回结果。
- **异步**：另提供一个工具发起长耗时命令，立即返回句柄；由 Agent 自行轮询查询命令信息。
- 理由：大语言模型足够聪明，可自行判断命令是否耗时，从而选择模式。

## 2. 团队评估

### 2.1 同意的部分

1. **双模式是成熟做法**，MCP 生态中常见"短任务同步、长任务异步"的划分。
2. **同步模式是最优的默认体验**：绝大多数命令（`ls`、`cat`、`systemctl status`）在秒级完成，一次往返拿到结果，无需轮询。
3. **异步模式是长耗时命令的必需品**：MCP 客户端自身有请求超时（通常约 60 秒），纯同步模型下长命令必然撞上客户端超时，Agent 会拿到误导性的错误。
4. **让 Agent 显式选择模式**，比隐式猜测更可解释——工具调用记录里能直接看到 Agent 的意图。

### 2.2 必须修正的一点：LLM 无法可靠预判耗时

客户的前提"模型能自己判断命令是否耗时"**在多数情况下成立，但不可靠**：

- 经验性低估：`apt-get update`、`npm install`、`docker build`、`make`、数据库备份等，实际耗时高度依赖网络与机器负载，模型无法预知；
- 隐藏交互：命令可能等待输入（确认提示、密码、`less`），表现为"卡住"；
- 网络抖动：本应秒级的命令因远端网络问题变成长耗时。

**如果同步工具在超时后直接返回错误，模型判断错的代价就很大**：Agent 会认为命令失败，可能重试，而远端命令其实还在执行，导致重复执行（例如重复 `apt-get install`、重复写入文件）。

### 2.3 修正方案：同步是"有上限的等待"，超时降级为异步

**同步工具超时后不报错，而是返回 `command_id` 与 `status: running`**，让 Agent 无缝转入轮询。这样：

- 模型判断对了 → 一次拿到结果；
- 模型判断错了 → 退化为异步，成本只是一次额外的轮询，**不会重试、不会重复执行**。

这条设计使双模式的正确性不依赖于模型的判断准确率，是整个方案成立的关键。

## 3. 建议的工具集合

三个 MCP 工具，底层共用同一套异步执行引擎：

| 工具 | 入参 | 返回 | 说明 |
| ---- | ---- | ---- | ---- |
| `run_command` | `terminal_id`, `command`, `wait_seconds?` | 完成：`status=completed`、`exit_code`、`output`、`duration_ms`；超时：`status=running`、`command_id`、部分输出 | 同步模式，默认等待 30 秒（可配置，上限 50 秒） |
| `run_command_async` | `terminal_id`, `command` | `status=running`、`command_id` | 异步模式，立即返回；等价于 `wait_seconds=0` |
| `get_command_status` | `command_id`, `include_output?`, `tail_lines?` | `status`（running/completed/failed）、`exit_code`、`duration_ms`、部分或完整输出 | 轮询用，对两种模式发起的命令都有效 |

补充说明：

- `run_command_async` 在实现上等价于同步工具等待 0 秒，**不重复实现执行逻辑**。
- 同步与异步发起的命令拥有相同的 `command_id` 语义，`get_command_status` 统一处理。
- 工具描述（description）中明确提示：**预期耗时超过 30 秒的命令请使用异步模式**，给模型提供判断依据。

## 4. 必须明确的并发语义：同一终端串行

> 客户提问："同一终端串行是什么意思？"本节专门解释。

### 4.1 一个"终端"在底层是什么

一个终端 = **一条常驻 SSH 会话 + 一个持续活着的 bash 进程**（方案 C）。所有命令都在这**同一个 bash 进程**里通过 `eval` 执行，因此它们共享同一个工作目录、同一份环境变量。

### 4.2 串行的含义

**同一终端，同一时刻只允许一条命令在执行。** 若在命令 A 执行期间又发来命令 B，B 不会插进去并行跑，而是**等 A 结束后再执行**（排队）。

具体时间线示例：

| 时刻 | Agent 动作 | 终端内实际发生 |
| ---- | ---- | ---- |
| T0 | `run_command_async("apt-get update")` | 命令开始执行，**占用该终端** |
| T1 | `run_command("ls -la")` | 终端忙 → 该命令**排队**，不执行 |
| T2 | 轮询 apt-get 状态 | 返回 `running`；`ls -la` 状态为 `queued` |
| T3 | apt-get 完成 | 返回输出与退出码，释放终端 |
| T4 | （自动） | 排队的 `ls -la` 开始执行，完成后返回结果 |

### 4.3 为什么必须串行（三个理由）

1. **状态共享冲突**：两条命令在同一 bash 进程中执行，若并行，`cd` 与 `export` 会互相覆盖。例如 A 执行 `cd /var/log` 的同时 B 执行 `cd /etc`，两条命令之后各自看到的目录将是随机的——"保留状态"的语义直接失效。
2. **输出无法切分**：包装脚本每执行完一条命令打印一个结束标记。若两条命令并行，输出会交错，标记无法对应到正确的命令，输出归属错乱。
3. **架构天然如此**：包装脚本是单进程 `read` 循环，读一条、执行一条、打印标记。并发需要引入多进程/多会话管理，复杂度大幅上升，且与"常驻状态"目标冲突。

### 4.4 需要并行怎么办

**跨终端并行不受限制。** Agent 若想同时跑多条长命令，为每个任务创建独立终端即可：

```
终端 T1 → apt-get update      （异步）
终端 T2 → docker build ...    （异步）
终端 T3 → tail -f /var/log/x  （异步）
```

三个终端各自独立串行，整体并行。这也是"每主机终端数量上限"（Q11）存在的原因。

### 4.5 终端忙时的两种落地方式（团队建议取 A）

| 方式 | 行为 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| **A. 排队**（建议） | 命令进入队列，等待前一条结束后自动执行；同步调用超时后返回 `status=queued` + `command_id` | 与人类在 shell 里连续敲命令的直觉一致；Agent 不会因为"终端忙"而失败 | 队列需要上限（建议 10 条），超出则拒绝，防止无限堆积 |
| B. 拒绝 | 立即返回错误 `terminal busy`，Agent 需自行换终端或稍后重试 | 行为更显式 | Agent 需处理错误分支，且容易误判为命令执行失败 |

状态取值相应扩展：`queued`（排队中）、`running`（执行中）、`completed`（已完成）、`failed`（执行出错）、`broken`（终端连接断开）。

跨终端当然可以并行。

## 5. 输出与流式

- **人类界面**：通过 Tauri 事件实时接收命令的流式输出，不受 30 秒限制，可一直观察直到结束。
- **MCP 返回**：同步模式在命令结束时一次性返回输出；超时/异步轮询时返回**已累积的输出**。
- **输出上限**：需设置单条命令的输出上限（建议默认 1 MB 或 20000 行，可配置），超出时截断并在返回中明确标注 `truncated: true` 与实际总长度，避免撑爆 MCP 上下文。二期可提供分段读取。

## 6. 已确认结论（Q4，2026-09-09）

1. **采纳**双模式：`run_command`（同步）+ `run_command_async`（异步）+ `get_command_status`（轮询）。
2. **采纳**同步超时降级为异步：超时返回 `command_id` + `status: running`，不报错、不中断远端命令。
3. 同步默认等待 **30 秒**、上限 **50 秒**，客户确认可以。
4. **同一终端串行**已接受；终端忙时采用 **A. 排队**，队列上限建议 10 条，超出则拒绝。
5. 状态取值：`queued` / `running` / `completed` / `failed` / `broken`。
