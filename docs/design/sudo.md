# sudo 提权设计

> 状态：已确认（Q33）
> 客户提案：提供"禁止注入 / 每次询问 / 自动注入"三种模式，由用户为每个主机选择。

> ⚠️ **投递机制即将变更（D47）**：本文 §3.3、§6.2、§7 各节描述的 **askpass + FIFO** 投递方式
> 是**当前实现**，但它无法抵御"同 UID 的 Agent 抢读密码"（V2 / C1）。
> 定稿方向是**双通道**——普通命令仍走数据面（本文其余部分不变），提权改由应用自建的
> 短命 SSH 通道以 `sudo -S` 投递，远端不再部署 askpass、不再建 FIFO。
> 实施后需重写相关章节；在此之前，**不要把 askpass + FIFO 当作最终设计**。
> 详见 [`docs/decisions.md`](../decisions.md) **D47**。

## 1. 客户提案

为每个 SSH 主机配置 sudo 密码处理策略，三选一：

| 模式 | 行为 |
| ---- | ---- |
| **禁止 sudo 密码注入** | Agent 执行 sudo 提权命令时自动拒绝 |
| **每次询问** | 用户为该主机预配置 sudo 密码；Agent 执行 sudo 时通过系统通知询问用户，用户决定允许或拒绝 |
| **自动注入** | 默认自动注入密码并执行 |

## 2. 团队评估

### 2.1 产品设计：赞同

- 把提权决策权交给用户，符合本项目"人类可管可控"的定位；
- 三种模式覆盖了不同信任等级的使用场景；
- 默认应为**禁止**（最安全），由用户显式放宽。

### 2.2 技术难点：需要先说清楚

**难点一：我们刻意不申请 PTY，而 `sudo` 默认从终端读密码。**
方案 C 没有 PTY，且每条命令的 stdin 指向 `/dev/null`，因此 `sudo` 会直接失败（`sudo: a password is required`）。这不是缺陷——它天然实现了"模式一：禁止注入"。

**难点二：如何把密码交给 `sudo`，且不落盘、不暴露给 Agent。**
可选手段：

| 手段 | 说明 | 评价 |
| ---- | ---- | ---- |
| `sudo -S` + 管道喂密码 | `printf '%s\n' "$PW" \| sudo -S cmd` | 简单，但要求命令改写，且密码需存在于某处 |
| 环境变量 | `export MF_SUDO_PW=...`，函数读取 | 同用户其他进程可经 `/proc/*/environ` 读到，**不推荐** |
| `SUDO_ASKPASS` 助手 | `sudo -A` 调用外部程序取密码 | **推荐**，可精确控制"何时给密码" |
| 远端保存密码文件 | 写入远端磁盘 | **禁止**，密码落盘 |

**难点三：命令改写很脆弱。**
若靠正则识别"命令里有没有 sudo"，遇到 `sh -c 'sudo ...'`、脚本内调用、`pkexec` 等情况会漏判。**因此不用改写，改用透明拦截。**

## 3. 推荐实现机制

### 3.1 第一步：优先尝试免密 sudo

会话建立时执行一次 `sudo -n true` 探测：

- **成功** → 该主机已配置 `NOPASSWD`，任何模式下都无需注入，Agent 直接执行即可（体验最好）；
- **失败** → 说明需要密码，进入下面的注入流程。

### 3.2 第二步：透明拦截 `sudo`

包装脚本中定义并导出 shell 函数：

```bash
sudo() { command sudo -A -p '' "$@"; }
export -f sudo
```

- `-A` 让 sudo 通过 `SUDO_ASKPASS` 指向的程序获取密码；
- `export -f` 使该函数对子 bash 进程（如 `bash script.sh`）同样生效；
- **不依赖命令改写**，Agent 照常写 `sudo apt-get install -y nginx` 即可。

### 3.3 第三步：密码投递（askpass + FIFO）

- 会话建立时在远端创建 askpass 脚本 `~/.mf-perch/askpass.<nonce>`（权限 `0700`，不含任何密钥）；
- **每次索要由 askpass 自己创建一条独立 FIFO**，用后即删：

  ```bash
  #!/bin/bash
  mfperch_fifo="$HOME/.mf-perch/sudopw.fifo.<nonce>.$$"
  umask 077; rm -f "$mfperch_fifo"; mkfifo "$mfperch_fifo" || exit 1
  exec 3<>"$mfperch_fifo"                                 # O_RDWR：永不阻塞
  printf '__MF_SUDO_REQUEST__<nonce>__%s__\n' "$$" >&2    # 必须写 stderr！
  IFS= read -r -t 120 mfperch_pw <&3                      # 兜底超时，见 §7.9
  rm -f "$mfperch_fifo"
  printf '%s\n' "$mfperch_pw"                             # 密码走 stdout
  ```

  > **为什么每次索要一条独立 FIFO（§7.8）**：FIFO 上一次写入只会被**其中任意一个**
  > 正在阻塞的读者取走。若多次索要共用一条 FIFO，应答就会错配——用户批准的
  > 那次可能拿到空密码而失败，而**被拒绝**的那次可能拿到密码而越权。
  > 令牌（askpass 的 PID）随标记回传，应用据此把应答精确投递到对应 FIFO。
  >
  > **实现要点（WSL 实测发现）**：`sudo -A` 会把 askpass 程序的 **stdout 第一行当作密码**。
  > 因此"请求标记"**必须写到 stderr**（`>&2`），密码才写 stdout。若标记走 stdout，
  > sudo 会把标记当成密码，认证必然失败（实测报 `Authentication failed`）。

- 应用通过**独立的 SSH channel** 向该次索要的 FIFO 写入应答（`test -p` 守卫 + `cat > fifo`，
  密码只走 channel 的 stdin），不占用命令通道，不进入命令帧协议；
- **密码不写入远端磁盘、不进入环境变量**，只在被索要时经内存传递。

### 3.4 三种模式的落地差异

| 模式 | 实现 |
| ---- | ---- |
| **禁止注入** | 不设置 askpass。`sudo` 因无密码而失败，应用将错误转成明确提示"该主机已禁用 sudo 提权" |
| **自动注入** | 收到 `__MF_SUDO_REQUEST__` 标记后，立即向 FIFO 写入密码 |
| **每次询问** | 收到标记后弹系统通知，用户允许则写入密码，拒绝或超时（60 秒）则**向 FIFO 写入空行**使 sudo 认证失败（初版此处写的是"关闭 FIFO → EOF"，已由 §7.3 修正）。同一条命令内拒绝只问一次，后续索要自动沿用（§7.10） |

### 3.5 密码来源

- 每个主机可选配置一个 **sudo 密码**，加密存储（复用 Q5 的字段级加密方案）；
- 提供"**复用 SSH 登录密码**"选项，避免用户重复录入。

## 4. 安全边界

- sudo 密码属凭据，**对 Agent 完全不可见**，绝不出现在 MCP 返回、日志或命令历史中；
- 命令历史中记录的 sudo 命令，密码部分不得落库；
- 模式一为**默认值**；用户切换到模式二/三时，界面需明确提示风险；
- 一切"未被拦截"的 sudo 调用（如 `sh -c`、非 bash 解释器、`pkexec`）都会因缺少密码而**失败关闭**（fail-closed），不会静默提权。

## 5. 已知限制（诚实记录）

1. **拦截范围有限**：`export -f` 对 bash 子进程有效；`sh -c`、`python` 等其他解释器、以及直接 `exec` 的二进制调用 `sudo` 时不生效——此时 sudo 失败，属安全默认。
2. **依赖远端 sudo 允许非交互**：若远端配置了 `Defaults requiretty`（老 RHEL 默认），非 PTY 下 sudo 会被拒绝。需在文档中提示，或由用户在远端调整。
3. **模式二需要人类实时在场**：无人响应时命令超时失败，Agent 会收到明确原因。
4. **FIFO 由 askpass 自清理**（读完应答即删）；askpass 脚本在会话结束时由会话清理脚本删除，异常退出留下的残留由下次会话建立时按 `-type f` 回收（不会误删 FIFO）。

## 6. 原理详解（客户要求展开）

### 6.1 坑二原理：`sudo` 函数如何实现透明拦截

**背景：shell 执行一条命令时，先查"函数表"，再查外部程序。**
bash 里输入 `sudo apt-get install nginx` 时，解析顺序是：别名 → 函数 → 内建命令 → `$PATH` 里的可执行文件。因此只要我们**先定义一个名为 `sudo` 的 shell 函数**，Agent 敲的 `sudo ...` 就会落到我们的函数上，而不是 `/usr/bin/sudo`。

**我们的函数做了什么：**

```bash
sudo() { command sudo -A -p '' "$@"; }
```

- `sudo()` — 定义同名函数，抢在 `/usr/bin/sudo` 之前被匹配。
- `command sudo` — `command` 关键字的作用是"跳过函数查找，直接执行外部命令"，否则会无限递归调用自己。
- `-A` — 让真正的 sudo 改用 `SUDO_ASKPASS` 指定的程序去取密码（见 6.2）。
- `-p ''` — 把 sudo 的密码提示语设为空，避免它往输出里打印提示文本，污染我们的输出解析。
- `"$@"` — 把 Agent 传进来的所有参数**原样转发**给真正的 sudo，所以 `sudo -u postgres psql` 这类带参数的调用也正常。

**`export -f sudo` 的作用：**
`export -f` 把函数体导出到环境变量中，让**子 bash 进程**也能继承这个函数。例如 Agent 执行 `bash deploy.sh`，脚本里的 `sudo` 调用同样会被拦截。若不加 `export -f`，只对当前 shell 直接输入的命令生效。

**为什么不用"改写命令"的方式：**
另一种思路是扫描命令字符串，发现 `sudo` 就替换成别的东西。但命令是任意文本，无法可靠解析：`sh -c 'sudo x'`、`echo sudo`、`python -c "..."`、变量拼接等情况下，字符串识别必然漏判或误判。用 shell 函数拦截是**语义级**的，只要 shell 解析到 `sudo` 这个词就走我们的函数，不依赖文本匹配。

### 6.2 坑三原理：密码如何被 `sudo` 取到，且不落盘

**第一步：`sudo` 平时从哪里读密码？**
`sudo` 默认从**控制终端**（`/dev/tty`）读密码。我们的会话刻意不申请 PTY，也没有终端，且命令的 stdin 指向 `/dev/null`，所以 sudo 读不到任何东西 → 失败。这正是"模式一：禁止注入"的天然实现。

**第二步：`-A` / `SUDO_ASKPASS` 是什么？**
`sudo -A` 表示"不要从终端读密码，改为执行 `SUDO_ASKPASS` 环境变量指向的程序，把该程序**打印到 stdout 的第一行**当作密码"。这是 sudo 官方提供的、给图形化程序用的标准机制（类似 macOS 的密码弹窗）。

**第三步：askpass 脚本做什么？**

```bash
#!/bin/sh
printf '__MF_SUDO_REQUEST__<nonce>__\n' >&2      # ① 告诉应用：现在有 sudo 在要密码（必须 stderr）
IFS= read -r pw < "$HOME/.mf-perch/sudopw.fifo"  # ② 阻塞等待密码
printf '%s\n' "$pw"                               # ③ 把密码打印给 sudo（stdout）
```

- ① 通过**标准错误**输出一个带随机串的标记，让应用知道"有人正在索要密码"；
  **注意：不能用 stdout**——sudo 会把 stdout 的第一行当作密码（WSL 实测确认）。
- ② 从 FIFO 读取密码——**这里会阻塞**，直到有人写入（见第四步）；
- ③ 把读到的密码打印到 **stdout**，sudo 收到后继续执行。

**第四步：FIFO 为什么能实现"应用把密码递给脚本"？**
FIFO（命名管道）是一个特殊文件，行为像一根管子：一端读、一端写。`read < fifo` 会一直**挂起等待**，直到另一端有数据写入。所以：

```
askpass 脚本  ──读──►  sudopw.fifo  ◄──写──  应用（经独立 SSH 通道）
```

应用在收到 ① 的标记后，通过**另一条独立的 SSH channel** 执行一条写命令，把密码写入 FIFO。脚本立即读到，转手交给 sudo。

**为什么用 FIFO，而不用普通文件或环境变量？**

| 方式 | 问题 |
| ---- | ---- |
| 写入普通文件 | 密码**落盘**，即使随后删除，磁盘上仍可能残留；会话异常中断时文件也可能遗留 |
| 放进环境变量 | Linux 下同用户的任何进程都能读 `/proc/<pid>/environ`，**密码会泄露给同机其他进程** |
| **FIFO（采用）** | 密码只在内存中经管道传递，**不落盘、不进环境变量**，读完即消失 |

**为什么另开一条 SSH 通道，而不是复用命令通道？**
命令通道的 stdin 正被命令帧协议占用（NUL 分帧），stdout 正被输出解析占用。如果往同一个通道里混入密码，会污染协议、破坏输出边界。所以单独开一条 channel 只做"写密码"这一件事，用完即关，互不干扰。

### 6.3 三种模式的分叉点

三种模式**共用上述全部机制**，唯一区别在于"收到 `__MF_SUDO_REQUEST__` 标记之后怎么做"：

| 模式 | 收到标记后的动作 | 结果 |
| ---- | ---- | ---- |
| 禁止注入 | 不设置 askpass（机制整体不启用） | sudo 拿不到密码，命令失败，应用翻译为"该主机已禁用 sudo 提权" |
| 自动注入 | 立即向 FIFO 写入密码 | sudo 拿到密码，命令继续执行 |
| 每次询问 | 弹系统通知 → 用户点"允许"才写密码；点"拒绝"或 60 秒超时则让 sudo 失败 | 允许则执行；拒绝/超时则 sudo 失败，Agent 收到明确原因 |

**安全默认（fail-closed）**：任何未被拦截的 sudo 调用（如 `sh -c 'sudo ...'`）都拿不到密码 → 失败，而不是静默提权。

## 7. 实现说明与实测修正（2026-09-10）

以下四点均为**端到端测试实测发现**，是实现阶段偏离初版设计的地方。初版设计文档的相应描述已被本节取代。

### 7.1 askpass 必须写 stderr（原设计已含，实测确认）

`sudo -A` 会把 askpass 的 **stdout 第一行当作密码**。因此"请求标记"必须写 stderr（`>&2`），密码才写 stdout。初版设计误将标记写 stdout，会导致 sudo 把标记当密码而认证失败。

### 7.2 必须先用 `exec 3<>fifo`（O_RDWR）打开 FIFO，再打印标记

**这是最关键的一处修正。** 初版 askpass 是"先打印标记、再 `read < fifo`"，应用侧则用 `cat > fifo`（O_WRONLY）写入。实测发现：

- 以 **O_WRONLY 打开 FIFO 会在无读者时永久阻塞**（POSIX 语义）；
- 初版时序下，应用侧写端可能先于读者启动，于是**永久阻塞**；
- 由于命令串行执行，这个阻塞会把**整条命令队列彻底卡死**（实测表现为命令永久 `running`，终端不可再用）。

修正为：askpass 先用 `exec 3<>"$fifo"` 以 O_RDWR 打开（**POSIX 保证不阻塞**），再打印标记，之后从已打开的 fd 读取。这样写端一定能找到读者。

### 7.3 "拒绝"改为写入空密码，而非关闭 FIFO

初版设计是"关闭 FIFO 让 `read` 得到 EOF"。实测发现该做法与 7.2 的 O_RDWR 打开方式不兼容：askpass 自身持有读写端，EOF 不会因外部关闭写端而出现。

改为**写入一个空行**：askpass 读到空密码交给 sudo，认证随即失败，命令正常结束并返回非零退出码。行为等价（sudo 失败），但可靠得多。

### 7.4 FIFO 按会话唯一命名

初版用固定的 `sudopw.fifo`。实测发现多会话并发时，后启动会话的 `rm -f` + `mkfifo` 会**替换同名文件节点**，使已在阻塞的读写方落在**不同 inode** 上各自永久挂起。

改为 `sudopw.fifo.<会话 nonce>`，并在会话初始化时清理本用户下同前缀的历史残留文件，从根本上消除互相踩踏。

### 7.5 免密 sudo 无需特殊处理（不必探测）

初版设计提到"会话建立时用 `sudo -n true` 探测是否已配 NOPASSWD"。实测表明**这一步并非必需**：

若远端已配置 NOPASSWD，`sudo -A` 根本不会调用 askpass（不需要密码），因此不会产生 `SudoRequest` 事件，也就不会有任何注入动作。三种模式在此场景下自然都正确工作，无需探测分支。

### 7.6 路径中的 `$HOME` 必须用双引号

会话初始化脚本与 sudo 函数定义中的路径若用单引号包裹（`'$HOME/...'`），**shell 不会展开变量**，会创建名为 `$HOME` 的字面量目录，导致 sudo 报
`Failed to run askpass program ... No such file or directory`。全部路径改用双引号。

### 7.7 验证结论

`src-tauri/tests/sudo_e2e.rs` 在真实 SSH 服务器上验证了全部行为组合：

| 场景 | 期望 | 结果 |
| ---- | ---- | ---- |
| `deny` + `sudo id -u` | 失败且不提权 | ✅ |
| `auto` + `sudo id -u` | 自动注入并返回 root | ✅ |
| `ask` + 允许 | 注入并返回 root，且确实产生过确认请求 | ✅ |
| `ask` + 拒绝 | 失败、不提权，且**队列仍可用**（防卡死回归） | ✅ |
| `ask` + 非 sudo 命令 | 不产生确认请求（避免打扰） | ✅ |
| `auto` + 密码不落普通文件 | 远端不得出现普通文件形态的 FIFO（V1 回归） | ✅ |
| **`ask` + 并发索要分别允许/拒绝** | 各得各的应答，不串（§7.8 回归） | ✅ |

### 7.8 每次索要必须独占一条 FIFO（B2，2026-09-11）

**问题**：初版用**一条会话级 FIFO** 承载该会话的所有索要。FIFO 的语义是
"一次写入只会被**其中任意一个**正在阻塞的读者取走"（POSIX 未规定是哪一个）。
当同一会话内出现两次并发索要（例如 Agent 执行 `sudo a & sudo b &`），
两个 askpass 会同时阻塞在同一条 FIFO 上，于是应答开始错配：

- 用户**批准** A 时写入的密码可能被 B 的 askpass 读走 → A 提权失败；
- 用户**拒绝** B 时写入的空行可能被 A 读走 → **被拒绝的那次读到了密码而提权成功**。

错配由**用户点击顺序**驱动，不是概率问题：应用按"用户决策顺序"写入应答，
而内核按"阻塞顺序"唤醒读者，两者不一致时就发生交换。

**修正**：每次索要一条独立 FIFO，名字含会话 nonce 与 askpass 的 PID
（`sudopw.fifo.<nonce>.<pid>`）；令牌随请求标记回传，应用按 `(nonce, token)`
精确投递应答。令牌会被拼进应用下发的命令，因此**只接受数字**，防止被伪造的
标记注入命令字符。

**为什么不做"同一终端只允许一个待决索要"**：这个更小的方案不成立。
askpass 在打印标记**之前**就已 `exec 3<>fifo` 成为读者，因此第二个索要的读者
必然先于应用的判断存在；此时再"拒绝第二个请求"的写入同样会被合法请求偷走，
反而把错配引入到原本正常的路径上。

**回归测试**：`concurrent_sudo_requests_do_not_cross_route`。编排上刻意让
"被允许的那次"先写入密码、"被拒绝的那次"后写入空行（先批准后弹出的对话框），
使旧实现必然把密码交给最先阻塞的读者。已验证：把路由临时降级回共用 FIFO 时
该测试**失败**，恢复后通过。

### 7.9 askpass 的兜底读超时（O4）

askpass 以 `read -r -t 120` 等待应答，比应用侧 60 秒确认超时留一倍余量：

- 正常路径永远由应用应答（注入密码或写空行拒绝），超时不参与；
- 只有应用侧异常（会话中断、进程崩溃）才会走到超时，此时读到空密码 →
  sudo 认证失败 → 命令照常结束，**不会把串行队列永久挂死**。

注：shebang 因此必须是 `#!/bin/bash`——Debian/Ubuntu 的 `/bin/sh`（dash）
不支持 `read -t`，会直接报错导致 sudo 永远失败。远端本来就要求有 bash。

### 7.10 拒绝会触发 sudo 重试——已按"一次询问"合并（Q36 / D44）

sudo 在密码错误时会重试（默认最多 3 次），`-A` 下每次重试都会**重新调用
askpass**，因此会产生新的索要与新令牌。端到端实测：一条被拒绝的
`sudo id -un` 共产生 3 次索要。

这本身是 sudo 的行为，不是缺陷；但若每次索要都询问人类，`ask` 模式下人类
要在「60 秒超时 × 3 次」的窗口里连点三次几乎相同的「拒绝」。

**现行实现**：按"当前命令"记住拒绝结果，其后续索要自动沿用拒绝、不再打扰人类。
记忆挂在运行时条目的当前命令上，命令结束即失效——**下一条命令照常询问**。

- 记住的范围：除「允许」外的所有结果（拒绝 / 超时 / 询问通道不可用），
  因为这三者都会让 sudo 重试；语义仍是 fail-closed，只是不再重复问。
- **只传播「拒绝」**：允许不被记住（否则人类只批准 `sudo a` 就会连带放行
  同一条命令里的 `sudo b`）；因此"密码配错、每次都点允许"仍会问 3 次。
- 拒绝只记在**发起询问的那条命令**上：人类在弹窗期间等待时，提问的命令可能已结束。
- 同一条命令内的 `sudo a && sudo b`：拒绝 `a` 后 `b` 也自动拒绝（范围取舍见 D44）。
- 审计区分来源：当场拒绝 / 超时 / 通道不可用 / 自动沿用各有独立备注，
  人类能看出自己只被问过一次。

## 8. 已确认结论（Q33，2026-09-09）

- 客户答复：**采纳三模式设计，且三种模式在一期（MVP）全部实现**。
- 结论：
  1. 每个主机可配置 sudo 策略：`deny`（禁止注入，默认）/ `ask`（每次询问）/ `auto`（自动注入）。
  2. 一期实现全部三种模式，包括 askpass + FIFO 密码投递机制、系统通知、超时处理、FIFO 清理。
  3. 默认值为 `deny`（fail-closed）。
- 范围影响：**sudo 提权由"二期"提升为"一期"**，MVP 范围相应扩大。开发需覆盖三种模式的测试（含无人响应超时、拒绝、密码错误等分支）。
- 前置条件（编码前需核实）：
  - 远端 sudo 版本支持 `-A` / `SUDO_ASKPASS`（sudo 1.6.9+，基本无风险）。
  - 远端允许非交互 sudo（`Defaults requiretty` 会阻断，老 RHEL 需用户调整）。
  - 系统通知在 Windows 上的落地方式（Tauri notification 插件）。
