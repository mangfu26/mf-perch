# 凭据存储设计

> 状态：待客户确认（对应问题清单 Q5）
> 客户决策：所有数据存放在同一个 SQLite 数据库中，敏感字段加密后存储（非明文）。

## 1. 客户决策与评估

### 1.1 客户决策

- 所有数据（主机、认证信息、终端、命令历史）统一存放在**同一个 SQLite 文件**中。
- 理由：后续可能实现数据备份与同步，单文件只需备份/迁移一个 SQLite 文件。
- SSH 密码、SSH 私钥等敏感字段**加密后存储**，不明文落库。

### 1.2 团队评估：方向正确

- 单文件 SQLite 便于备份、迁移与同步，与客户目标一致；
- 字段级加密保证敏感信息即使数据库文件泄露也不可直接读取；
- 元数据（主机名、终端名、命令历史）保持明文可读，便于 UI 展示、搜索与审计。

**但有一个前提必须解决：加密密钥不能存放在同一个 SQLite 文件中。**
否则拿到数据库文件即可解密，加密形同虚设。密钥必须存放在**数据库之外**。

## 2. 加密方案（建议）

### 2.1 加密粒度：字段级加密（推荐）

| 数据 | 是否加密 | 说明 |
| ---- | ---- | ---- |
| 主机地址、端口、名称 | 否 | 元数据，人类需在 UI 查看 |
| 认证信息名称、用户名 | 否 | 元数据 |
| **认证密码** | **是** | 敏感 |
| **SSH 私钥内容** | **是** | 敏感 |
| **私钥 passphrase** | **是** | 敏感 |
| 终端名称、状态 | 否 | 元数据 |
| 命令历史（命令、输出） | 否 | 审计需要，人类可读；若客户要求也可加密 |

- 算法：**AES-256-GCM**（或 XChaCha20-Poly1305），认证加密，防篡改。
- 每个字段独立随机 nonce，与密文、认证标签一同存储。
- 存储格式建议：`v1:<nonce_b64>:<ciphertext_b64>`，带版本号便于将来更换算法。

### 2.2 备选：整库加密（SQLCipher）

- 使用 SQLCipher 加密整个数据库文件，元数据也一并加密。
- 优点：实现统一，单文件 + 单密钥。
- 缺点：密钥管理问题完全相同；元数据不可直接查看，调试与外部工具访问不便；Rust 侧依赖 `rusqlite` 的 `bundled-sqlcipher`，打包体积与构建复杂度略增。
- 结论：**不推荐**，除非客户希望连元数据也加密。

## 3. 密钥管理（关键决策点）

> 客户质疑：如果采用 K1（系统钥匙串），是不是又遇到"Linux 下没有安装密钥服务"的问题？
> 是的，这是同类风险。本节给出分层探测 + 显式降级的设计，遵循工程原则 P1 / P2。

加密密钥从哪来、放哪里，是本设计的核心。三种方案：

| 方案 | 密钥来源 | 用户体验 | 安全性 | 备份/同步友好度 |
| ---- | ---- | ---- | ---- | ---- |
| **K1 系统钥匙串** | 随机 32 字节主密钥，存入 OS 凭据管理器（Windows 凭据管理器 / macOS 钥匙串 / Linux Secret Service） | 无感，无需输入密码 | 高，依赖 OS 保护 | 中：换机器需转移主密钥 |
| **K2 用户主密码** | 用户设置主密码，用 Argon2id 派生密钥 | 每次启动需输入（可"记住"一段时间） | 高，不依赖 OS | 高：新机器输入同一主密码即可解密 |
| **K3 本地密钥文件** | 随机密钥写入应用数据目录下的文件（权限保护） | 无感 | 低：备份文件或同机程序可能读到 | 高：随数据库一起迁移 |

### 3.1 各平台的钥匙串可用性（探测结论）

| 平台 | 钥匙串实现 | 可用性 |
| ---- | ---- | ---- |
| Windows | Credential Manager | 几乎总是可用 |
| macOS | Keychain | 几乎总是可用 |
| Linux | Secret Service（gnome-keyring / KWallet 等） | **不保证**：无桌面环境、精简 WM、容器、服务器版可能缺失 |

补充说明：本应用是 Tauri **桌面 GUI** 应用，无图形环境的主机本身无法运行（需 X11/Wayland）。因此 K1 的真实风险面主要是"**Linux 桌面环境但未安装 Secret Service**"（如 i3 / sway 等精简窗口管理器），而非完全无头服务器。风险面比 `base64` 那次小，但仍必须处理。

### 3.2 分层降级设计（建议）

启动时按顺序探测，**绝不静默降级**：

```
1. 尝试 K1（系统钥匙串）
   ├─ 可用 → 使用 K1，界面显示"已由系统钥匙串保护"
   └─ 不可用 ↓
2. 明确告知用户："当前系统未提供密钥服务，需要选择保护方式"
   ├─ 选项 A：设置主密码（K2）→ 安全强度不降低，推荐
   └─ 选项 B：使用本地密钥文件（K3）→ 界面明确标注风险
3. 用户选择后，将所选方式记录在数据库中（仅记录方式，不记录密钥）
4. 若此前已用某方式加密，但该方式当前不可用（如钥匙串被卸载）
   → 提示用户"凭据无法解密"，并提供恢复/迁移路径，而不是清空数据
```

关键点：

- **方式记录在数据库元数据中**（如 `key_provider = 'keyring' | 'master_password' | 'local_file'`），应用据此选择解密路径。
- **K2 的校验**：用 Argon2id 派生密钥，存 salt 与校验值；密码错误时明确提示，不清空数据。
- **K3 的防护**：密钥文件权限 `0600`（Unix）/ 仅当前用户可读（Windows），并在界面标注"安全性低于钥匙串"。
- **不引入新的外部命令依赖**：探测与降级逻辑全部用 Rust 实现，不调用系统命令行工具。

### 3.3 团队建议

**分层策略（K1 优先 + 显式降级）**，理由：

- Windows / macOS 用户获得无感体验（覆盖绝大多数桌面用户）；
- Linux 无钥匙串时可降级到 K2 主密码，**安全强度不降低**；
- 密钥与数据库物理分离，满足"库文件泄露也无法解密"；
- 降级路径显式告知，符合原则 P1 / P2。

### 3.4 关于"备份与同步"的补充说明

客户提到后续可能做备份/同步。跨机器恢复时需要解决密钥迁移，可选做法（二期）：

1. 提供"导出加密备份"：用用户输入的密码对数据库重新加密，导出为可迁移文件；
2. 或提供"显示/导入主密钥"入口，由用户手工转移；
3. K2（主密码）天然适合跨机器恢复。

以上均属二期范围，MVP 阶段不实现。

## 4. 其他安全约束

- 明文凭据只允许短暂存在于内存，用后清零（`zeroize`）。
- **凭据绝不通过 MCP 工具返回给 Agent**；Agent 创建终端时只传 `host_id`，由应用内部查找该主机绑定的认证信息。
- 数据库文件位于应用数据目录（`%APPDATA%/mf-perch`），并设置合理权限。
- 日志中禁止输出密码、私钥、passphrase，即使是调试日志。

## 5. 已确认结论（Q5 / Q31，2026-09-09）

客户答复：**接受**。具体：

1. **数据存储**：所有数据（主机、认证信息、终端、命令历史）存于**同一个 SQLite 文件**，便于备份与迁移。
2. **敏感字段加密**：SSH 密码、SSH 私钥、passphrase 加密后存储（AES-256-GCM 或 XChaCha20-Poly1305），非明文。
3. **密钥管理采用分层降级**：K1 系统钥匙串优先；不可用时**显式**让用户选择 K2 主密码或 K3 本地密钥文件，绝不静默降级（遵循 P1 / P2）。
4. **命令历史不加密**：默认明文存储，便于人类审计与搜索；如后续需要，可在设置中提供可选项（二期）。

### 5.1 仍需注意的边界

- 加密主密钥**不得**存放在同一个 SQLite 文件中，必须物理分离。
- 明文凭据仅短暂驻留内存，用后 `zeroize`。
- 凭据绝不通过 MCP 返回给 Agent；Agent 创建终端时只传 `host_id`。
- 日志禁止输出密码、私钥、passphrase。
- 若用户所选密钥方式失效（如钥匙串被卸载），提示"凭据无法解密"并提供恢复路径，**不清空数据**。
