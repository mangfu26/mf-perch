# D49 — 数据面 `sudo` 明确拒绝；旧的 askpass/FIFO 投递机制整体移除

> 日期：2026-09-16  索引：[decisions.md](../decisions.md)
> 状态：现行（若与代码冲突，以代码与索引中标注的取代关系为准）。

> 条目自述状态：已实施（R4，客户 2026-09-16 明确"应该拒绝"）。


- **日期**：2026-09-16
- **状态**：**已实施**（R4，客户 2026-09-16 明确"应该拒绝"）。
- **背景**：D47/D48 把提权移到应用自建的**独立特权通道**（`run_as_root`）之后，
  数据面**已经完全没有任何密码来源**：不部署 askpass、不建 FIFO、没有环境变量。
  此时若对数据面上的 `sudo` 不作处理，Agent 会收到 sudo 自己的原始报错
  （`no tty present` / `a password is required` / `sorry, you must have a tty`），
  既难懂又容易被误判为环境问题而反复重试。
- **决策（客户拍板）**：**数据面通道不允许提权，必须明确拒绝**。
  包装脚本在读取循环之前注入一个 `sudo` shell 函数垫片
  （`protocol::sudo_reject_shim`），把 `sudo` 拦成"非 0 返回 + 一句可操作说明"。
- **文案随策略区分**（否则是误导）：
  - 允许提权的策略（`ask` / `auto`）：指引 Agent **改用 `run_as_root` 工具**；
  - `deny` 策略：说明**该主机已禁用提权**，并指出由人类在主机设置中开启——
    此时不应引导去用 `run_as_root`（那条路同样会被拒绝，只会让 Agent 白试一次）。
- **为什么用 shell 函数而不是 PATH 上的可执行文件**：不落任何远端文件、不依赖
  远端工具、随会话消失；`export -f` 之后对 `bash -c` 子进程同样生效
  （Agent 的命令常常在自己的 bash 里跑）。
- **随之移除的旧机制**（这是 V2 的成因所在，也是 V1 明文落盘的现场）：
  `askpass_script` / `sudo_fifo_name` / `is_valid_sudo_token` /
  `session_setup_script` / `session_cleanup_script` / `sudo_function_def` /
  `SUDO_REQUEST_PREFIX` / `SessionEvent::SudoRequest` / `SessionOutput::SudoRequest` /
  `send_sudo_password` / `deny_sudo` / `handle_sudo_request`，以及 Q36 的
  "同一命令只问一次"记忆（`sudo_denied` 等）。
- **Q36 的成因随机制消失**：该问题源于"拒绝 → 空密码 → sudo 重试 → 再次索要"
  的连环询问。`run_as_root` 是单命令形态，一次调用只提权一次、也就只问一次，
  因此不再需要"已拒绝"的记忆状态（`AskOutcome::DeniedByMemo` 已删）。
- **新增的可验证不变式**：**远端不再产生任何本应用的文件**。
  会话初始化阶段只剩环境快照（D4），`$HOME/.mf-perch` 的整套清理逻辑
  （连同 V1 缺陷的时序不变式）整体不再需要。e2e 用**前后快照对比**验证
  "本次操作不新增痕迹"——刻意不依赖机器上是否有旧机制的残留
  （实测本机就残留着 2026-09-11 的两个 FIFO；断言绝对值为零会把"机器不干净"
  误报成"实现又写了文件"，违反 AGENTS.md §5.4）。
- **保留不变**：三种模式（`deny` / `ask` / `auto`）仍然成立，含义收敛为
  "**是否允许 Agent 经 `run_as_root` 提权**"；`ask` 仍走系统通知征得人类同意。
  数据面上的 `sudo` 在**三种模式下都被拒绝**——这一点本身就是权限边界。
- **相关**：D47（双通道）、D48（提权取数）、D11 / Q33（三模式来源）、
  `docs/security-audit.md` V1 / V2、`docs/design/sudo.md`。
