# D58 — 更新提示的下载入口指向该版本的 Release 页面

> 日期：2026-09-22  索引：[decisions.md](../decisions.md)
> 状态：现行

- **决策**：应用提示"发现新版本"时，界面上的按钮打开**该版本的 Release 页面**
  （`…/releases/tag/vX.Y.Z`），**不是**本平台安装包的直链。
  - 清单（`update.json`）**新增字段 `release_url`**：有则直接用；
  - 缺失时由应用从 `platforms.<键>.url` **按 Release 直链的固定布局推导**：
    `…/releases/download/<tag>/<文件>` → `…/releases/tag/<tag>`；
  - 两者都拿不到（直链不是 Release 布局、又没写 `release_url`）时才没有按钮，
    界面退回"请到仓库 Releases 列表自行查找"；
  - 发布流水线在生成清单时写入 `release_url`（**D54** 的 "Publish update manifest to main"）。
- **性质**：**纠正 D23 第 1 点的实现偏差**。D23 写的就是"提示用户到 Release 页下载覆盖安装"，
  实现里却把 `download_url` 直接给了 `.msi` 直链——语义在决策里对、在代码里错，
  本条把代码拉回决策，并把"发布页"这一目标固化成契约。
- **理由**：
  1. 同一个 Release 下并列多种安装包：**Windows 就有 msi 与 setup.exe 之分**，
     将来多平台还要替用户挑平台（平台标识见
     [`update-manifest.md`](../update-manifest.md) §2）。给直链等于**替用户做了他该做的选择**；
  2. 直链路径含文件名，**文件名一变即 404**；发布页只含 tag，天然稳定；
  3. 修复了一处死路：旧实现里清单**缺当前平台条目**时 `download_url` 为空，
     用户被告知"有新版本"却**没有任何可点入口**。发布页与平台无关，永远有入口。
- **兼容性**：推导分支让**不知道新字段的镜像源与自建源**（**D42** 允许用户覆盖更新源）
  继续可用——它们照旧只给 `platforms.<键>.url`，应用仍能给出正确的发布页。
  反向（旧版应用读到新清单）只是忽略未知字段，行为不变。
- **影响（前后端契约三侧同步）**：
  - Rust：`UpdateManifest` 增可选 `release_url`；`UpdateStatus::Available` 的
    `download_url` 改为 `release_url`（推导逻辑 `release_page_from_download`）；
  - 前端：`src/stores/update.ts` 同步字段名；设置页按钮文案改为「前往发布页下载」，
    SHA256 一行明确标注为**本平台安装包**的校验值（发布页上可能有多个包，
    不标注会让人拿错包去核对）；
  - CI：`.github/workflows/release.yml` 生成的清单多写一行 `release_url`；
  - **不变的红线**（仍遵 D23）：不自动下载、不自动安装、不自动打开浏览器，
    用户点击才跳转；`sha256` 只展示供人工核对，不做自动校验。
- **相关**：**D23**（更新检查总方案）、**D42**（内置默认源 + 可覆盖）、
  **D54**（发布流水线）、**D55**（清单落仓库根、流水线自动回写）。
