# D40 — 落实 D22：终端事件推送，界面跟随 Agent 实时更新

> 日期：2026-09-11  索引：[decisions.md](../decisions.md)
> 状态：现行（若与代码冲突，以代码与索引中标注的取代关系为准）。


- **日期**：2026-09-11
- **决策**（落实 D22 已承诺的"应用内实时状态更新"）：
  1. 终端运行时发布**领域事件**：`TerminalCreated`、`TerminalRemoved`、
     `CommandStarted`、`CommandFinished`、`SessionChanged`（含状态与人类可读原因）。
  2. 运行时**不依赖 Tauri**：事件经无界 channel 交给外壳层（`lib.rs`）转发为
     单一 Tauri 事件 `terminal://event`（负载带 `kind` 标签）。
     与 `sudo://request` 的注入模式一致，因此运行时可在测试中直接订阅断言。
  3. **尽力而为的投递**：事件只用于"界面新鲜度"，真实状态始终以数据库为准，
     因此不阻塞、不回压、不重试；接收端关闭（应用退出）时静默跳过。
  4. 前端在 store 层订阅，收到事件后**去抖 250ms** 刷新终端列表；
     命令类事件且与当前查看的终端相关时，同时重放最近一次历史查询。
  5. **兜底校准**：窗口重新可见/获得焦点时主动刷新一次——托盘常驻（D16）下
     窗口可能长时间隐藏，事件推送不保证被消费。
  6. 顺带关闭 D39 的已知待办：输出泵检测到断开时**把状态落库为 `broken`**
     （此前只有应用重启才会落），界面与数据库都真实反映断线。
- **背景**（客户实测反馈）：
  - 问题①：Agent 触发自动重连后，审计页仍显示"连接已断开…你也可以点重连"，
    要人工点一次按钮才消失——审核者可能误以为终端仍未恢复。
  - 问题②：Agent 执行的命令不会实时出现在审计页，必须人工点刷新。
  - 两者**同一根因**：前后端之间此前只有 sudo 一条推送通道，其余全靠页面挂载时
    拉取一次。后端数据本身是对的（重连后状态已是 `active`），是界面陈旧。
- **影响**：
  - 新增 `src-tauri/src/terminal/events.rs`（事件枚举、通道、事件名常量）；
    `TerminalRuntime` 增加 `set_event_sink` / `emit`，`TerminalEntry` 共享同一槽位
    （已运行的输出泵也能发事件）；输出泵增加落库 broken。
  - `lib.rs` 装配事件转发；`RunOutcome` 的 `session_reconnected` 语义不变。
  - 前端：`stores/terminals.ts` 增加 `startListening` / `stopListening` /
    `refreshHistory`，`App.vue` 订阅事件并注册焦点校准。
  - 测试：新增单测（归档/删除必须发事件、未注入出口时不得 panic）；
    既有 e2e `run_command_auto_reconnects_broken_terminal_after_restart`
    扩展为同时断言 `session_changed` / `command_started` / `command_finished`。
- **相关**：D22（本次即其落地）、D39（重连）、D16（托盘常驻）、D19/D25（人类是审核者）。
- **不做**：命令完成的**系统通知**仍按 D22 留在二期；命令输出内容不走事件通道
  （界面需要输出时按 `command_id` 走既有 IPC 拉取），避免把大段输出塞进事件。
