# D32 — 工具 schema 的可空参数用 `anyOf` 表达，不用数组形式 `type`

> 日期：2026-09-10  索引：[decisions.md](../decisions.md)
> 状态：现行（若与代码冲突，以代码与索引中标注的取代关系为准）。


- **日期**：2026-09-10
- **决策**：MCP 工具的 `inputSchema` 中，可空参数一律表达为
  `"anyOf": [{...}, {"type": "null"}]`，**不使用** `"type": ["integer", "null"]`；
  并让该 schema 内联展开，避免出现 `$defs` / `$ref`。
- **背景**：客户用 `npx @modelcontextprotocol/inspector` 实测时，`create_terminal`、
  `run_command`、`run_command_async`、`get_command_status`、`list_terminals`
  五个工具被标记 `Schema portability: 0 error(s), 1 warning(s)`，警告字段正是
  各工具的可空参数（`name` / `wait_seconds` / `tail_lines` / `host_id`）。
  - 根因：`schemars` 1.x 默认把 `Option<T>` 生成为 `"type": ["<T>", "null"]`。
    这是合法的 JSON Schema 2020-12，但部分 MCP 客户端只接受 `type` 为**单个字符串**，
    遇到数组会告警、丢弃该约束，个别客户端甚至拒绝整个工具——"能连上但工具用不了"。
  - 该告警只是**兼容性提示**，不是功能故障：我们的 server 与严格客户端都能正确处理。
    但既然有零成本、语义等价的规避方式，就应当规避。
- **影响**：
  - 新增 `Nullable<T>` 包装类型（`#[schemars(with = "Nullable<T>")]`），
    仅参与 schema 生成，不改变 `Option<T>` 字段的序列化与反序列化行为。
  - 字段类型保持 `Option<T>` 且必须同时保留 `#[serde(default)]`，否则会变为必填。
  - 新增回归测试：`tool_schemas_do_not_use_array_type`、`tool_schemas_have_no_refs_or_defs`、
    `optional_params_use_anyof_with_null`、`optional_params_accept_absent_and_null`。
    schema 的**内容**契约由 `src/mcp/tools.rs` 的单测在进程内守住（那里能遍历
    `tool_router()` 的全部工具）；MCP e2e 中重复的内容断言**已删**，那里只保留
    端到端事实：经真实 HTTP `tools/list` 取回的每个工具 `inputSchema.type` 为 `"object"`。
  - 后续新增带可选参数的工具时，凡 `Option<T>` 字段都需加 `#[schemars(with = "Nullable<T>")]`，
    否则会重新引入告警。
