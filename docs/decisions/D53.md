# D53 — 文档与注释的三条书写规范：单一落点、只写现行事实、表述环境无关

> 日期：2026-09-18  索引：[decisions.md](../decisions.md)
> 状态：现行

- **决策**：为 `docs/` 与代码注释确立三条书写规范，已写入
  [`AGENTS.md`](../../AGENTS.md) §4.3（规则 2 / 6 / 7），本条记录其理由与判据。
  1. **同一知识点只允许一处权威落点，禁止复述**，提及时只引用
     （文件路径 / `D<编号>` / `Q<编号>` / `P<编号>`）；
  2. **只写现行事实 + 一行理由，不写流水账**；
  3. **表述必须环境无关**——写成"条件 + 机制"，不写成某台机器的事实。
- **背景**：项目尚在首发前，文档已开始积累历史包袱，客户提出"是否该清除、让项目瘦身"。
  团队评估后的结论是：**包袱不在"记录了历史"，而在三种具体的书写方式**，
  因此不采取"首发后一律不记 / 删掉历史说明"这种一刀切，而是给出可执行的判据。
  量化依据（2026-09-18 实测）：`docs/` 的 Markdown 共 **3401 行**，其中决策分片 1316 行、
  排错文档 538 行、需求清单 417 行；而 `src-tauri/` 注释里真正属于流水账的只有十几处。
  **瘦身的主战场是文档写法，不是注释数量。**
- **三条的机制与判据**：
  1. **复述必然长成冲突**，而不是长成冗余：同一事实写第二遍后，两份会各自继续被修改，
     读到哪一份取决于运气。故落点分工表成为规则的一部分（决策 → ADR；术语 → 术语表；
     MCP 契约 → `mcp-tools.md`；主题令牌 → `src/styles/theme.css`；环境排错 →
     `development-troubleshooting.md`），**新增事实先对上表，对不上就问客户**。
  2. **判据（一句话决定留不留）**：*删掉这段，下一个接手的 Agent 会不会重新提出这个
     已被否掉的方案？*
     - 会 → 留，但**压成一行护栏**（例：`不要对外声称支持 ProxyJump（D45）`）；
     - 不会 → 删（例：某个中间版本实现过又整体移除的代码形态描述）。
     改动过程由 `git log` 承担（提交信息规范见 AGENTS.md §2，因果链本就在历史里）。
     **例外（必须留）**：残余风险与能力边界（`security-audit.md` V2、`requiretty` 不支持提权）、
     以及 P3 / P4 那类能区分对错实现的教训——那是学费，删了等于退款。
  3. **无法假设后续接手者的机器比谁更好或更差**，所以环境相关的事项要写成条件句。
     反例 → 正例：
     `本机是机械硬盘，所以 -j 调大更慢`
     → `target` 位于机械硬盘（随机 I/O 受限）时，提高并行度只是把瓶颈从 CPU 换到内存与磁盘。
     具体读数**保留但降级**为标注日期与取法的**示例依据**，用来支撑机制判断，
     **不作为规则的适用前提**。此条同样约束代码注释：写"这个不变量为什么重要"，
     不写"我这台机器上它表现如何"。
- **取代关系**：不改写旧条目正文。本条只约束**此后新增与顺手修改**的写法；
  存量文档按本轮范围收敛（见下"影响"），不追求一次性重写。
- **影响**：
  - AGENTS.md §4.3 规则 2 扩写为"单一落点 / 禁止复述 / 只引用 / 落点分工"，新增规则 6、7；
  - `docs/development-troubleshooting.md` 中与并行度相关的一节由"本机实测评估"改写为
    "条件 + 机制"，机器读数降级为带日期的示例依据；
  - 代码注释中的日期署名与"曾 / 初版 / 已随 Dxx 移除"式过程叙述被清除，
    **`D<编号>` 锚点全部保留**（它是跨语言外键，见 D52）；
  - 交付前把"同一知识点只留一处"作为**收敛要求**持续执行，不单独立项。

  D45（ProxyJump 边界，护栏写法范例）、D7（工程原则 P1 / P2）。
