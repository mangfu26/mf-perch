# D60 — 登录身份本身是特权用户时不走 `sudo`：标记落在认证信息上

> 日期：2026-09-22  索引：[decisions.md](../decisions.md)
> 状态：已实施。

- **背景（客户提出，Q42）**：认证信息里配的本就是 root 时，"提权"这一步根本不存在，
  但主机表单仍要求配置提权口令来源；`ask` / `auto` 变成无意义的必填负担。
- **关键洞察（为什么不能拿 `deny` 当答案）**：`deny` 的语义是"拒绝**提权**"，而数据面通道
  跑的就是登录身份本身——在 root 主机上 Agent 的普通命令**本来就是 root**。
  此时 `deny` 挡住的只是 `run_as_root` 这一个工具入口，挡不住任何实际的特权执行。
  把"这台机器不需要提权"表达成 `deny` 是**假的安全感**（违反 P2 的"如实"），
  必须有一个诚实的表达位置。
- **决策**：**"这个身份登录后是不是特权用户"是身份的属性，不是主机的属性**，
  因此落在 `Credential::is_privileged`（布尔，由人类声明），
  而 `hosts.sudo_policy` **保持三档**（`deny` / `ask` / `auto`，语义不变）。
  - **为什么不是主机上的第四档策略**：主机只管"目标地址 + 用哪份凭据认证"，
    身份属性归凭据。同一份凭据可被 N 台主机引用，做成主机档就要逐台改；
    做成凭据标记则**换凭据即换语义**，无需同步。
    （本条最初实现为主机第四档 `not_needed`，客户在 dev 实测后指出角色混淆与逐台改档的负担，
    据此改到凭据上。**不要把"是否特权"再做成 `sudo_policy` 的一个取值**。）
- **运行期规则（短路只免掉"提权"，不免掉授权）**：
  1. **`deny` 优先**：策略为 `deny` 时 `run_as_root` 一律拒绝，即使绑定的凭据是特权身份。
     少了这条优先序，特权身份会把 `deny` 变成摆设（fail-open）；
  2. **特权身份 + `ask` / `auto`**：不包 `sudo`、不取口令、不弹确认，直接用该主机的
     环境加载方式起 bash（`privileged_launch_command()` 分流）；
     `sudo_password_source` / `sudo_password` 两列**一律忽略但不删**，取消标记后无需重填；
  3. **普通身份**：维持 D47 / D48 / D49 的既有行为。
- **声明与核验**：声明只表达意图，**事实仍由远端核实**——身份核实
  （`${EUID}` + `id -un`，D47）在包装脚本里，与该标记无关，因此声明错了（该用户实际非 0）
  仍会按现有逻辑**如实告警**，不会静默把"以为是 root"当成"是 root"。
- **数据面仍然拒绝 `sudo`（D49 不变）**，只换文案：特权身份下垫片提示"已以特权身份登录，
  直接执行即可"，而**不是**"改用 `run_as_root`"——后者会把 Agent 引向一条本不需要的往返。
  各情形的拒绝理由见 `src/ssh/protocol.rs` 的 `sudo_reject_shim()`。
- **顺带的能力边界变化**：该路径不经 `sudo`，因此**少一层 `env_reset`**，
  也**不再受 `Defaults requiretty` 限制**（该选项约束的是 sudo 申请 TTY 的行为）。
  这是机制推导，**未做真实 root 登录主机的端到端实测**（见"未实测"）。
  `requiretty` 主机"不支持提权"这条对外边界**只对 `ask` / `auto` 成立**，
  已在 `AGENTS.md` §4.4 同步收窄。
- **数据库迁移（触发 D50 的条件条款）**：`SCHEMA_VERSION` 1 → **2**，V2 为
  `ALTER TABLE credentials ADD COLUMN is_privileged INTEGER NOT NULL DEFAULT 0`。
  - **为什么这次必须迁移**：D50 当初"刻意不迁移"的前提是**产品未发布**，
    并写明"首发前若已存在用户库，则必须改回迁移方案"。`v0.1.0`–`v0.1.2` **已发布**
    （三个 tag，见 D54 流水线），它们装出来的库全是 V1 形状，故本条起恢复增量迁移。
  - **`DEFAULT 0` 即 fail-closed**：存量凭据升级后一律按"普通身份"处理，
    不会因为缺列而被误判成免提权。
  - **只增列、不重建表**：常量默认值的 `ADD COLUMN` 是元数据变更，不重写行；
    相比"重建 `hosts` 以放宽 CHECK"的旧实现，这里没有 `DROP TABLE`，
    因而**不存在级联删掉 `terminals` / `commands` 审计数据的风险**，也不需关外键。
  - **`V1_SCHEMA` 冻结为历史形状**（与已发布版本逐字节一致）：结构变化只由 `migrate()`
    的增量步骤负责。就地改 V1 会让"新建库"与"存量库升级后"两种形状不一致，
    等于制造第二个 V1。
- **暂缓（不要当成已实现）**：**"运行期探到 uid=0 后反向提示人类改标记"** 未做。
  保存期无法建立 SSH 连接去实测，而运行期已有的 `uid≠0` 告警覆盖了另一侧的错误
  （声明是 root 而实际不是）。等真有需求再评估，不要顺手加。
- **已知缺口（登记为 Q43，待客户定）**：特权身份下数据面的普通命令同样以 root 执行，
  而命令历史里的 `[特权用户(uid=0)]` 前缀目前**只打在 `run_as_root` 上**——
  审计视图会看不出"这台机器上 Agent 的每条命令都是 root"。
- **未实测（诚实标注）**：真实 **root 登录**主机的端到端。测试环境需要 sshd 开
  `PermitRootLogin`，属改动客户机器的事，已向客户请求授权、尚未得到答复；
  拿到授权前**不要**在测试环境自行打开该选项，也不要声称该路径"已实测通过"。
- **测试（能区分对错实现，§5.7 / P3）**：
  - `only_a_privileged_login_launches_the_privileged_channel_without_sudo`（`ssh/protocol.rs`）——
    判别性用例：普通身份必须出现 `sudo -S -p ` 与密码提示标记，特权身份必须**既不出现** `sudo `
    **也不出现**提示标记。把短路写反、或在普通身份漏掉包装，都会红灯；
  - `wrapper_script_always_installs_reject_shim` / `reject_shim_refuses_and_guides_to_the_tool`——
    **三档 × 两种身份都要装垫片**（漏一格就出现"数据面能静默提权"的洞），且特权身份的文案
    不得出现"口令 / `sudo -S` / `run_as_root`"，也不得与 `deny` 文案相同；
  - `upgrading_a_v1_database_adds_the_flag_without_losing_rows`（`store/db.rs`）——
    手工建 V1 库（其 `credentials` **没有**该列）+ 一行 host / terminal / command，迁移后断言：
    `secret_enc` **原样不变**（不重新加密）、新列默认 0、显式置位的行仍为 1、
    `hosts.sudo_policy` 写 `not_needed` **仍被 CHECK 拒掉**（第四档没有回流）、子表记录仍在；
  - `fresh_database_matches_the_upgraded_shape`——新建库与升级后的库形状一致（列存在、默认 0）；
  - `privileged_flag_roundtrips_through_every_read_path` / `toggling_the_flag_survives_a_name_only_update`
    （`store/credentials.rs`）——该标记在 `get` / `is_privileged` / `list_summaries` 三条读路径
    一致，且"只改名字的编辑"不会把它清掉（表单字段没接到 SQL 列那一类缺陷的形状）；
  - `save_host_accepts_privileged_credential_without_any_password`（`ipc/tests.rs`）——
    **同一份配置**（密钥凭据 + 无任何口令）在普通身份下被 `auto` 拒、标记为特权身份后必须放行；
  - `validate_skips_password_for_a_privileged_login`（`terminal/sudo.rs`）——
    保存期校验对特权身份免口令，普通身份仍要求口令。
