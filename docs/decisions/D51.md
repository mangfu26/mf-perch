# D51 — 构建遇阻禁止"绕过手段"：一律向客户求助，由客户退出 app 实例

> 日期：2026-09-18  索引：[decisions.md](../decisions.md)
> 状态：现行（若与代码冲突，以代码与索引中标注的取代关系为准）。

> 条目自述状态：已确定（客户拍板）。


- **日期**：2026-09-18
- **状态**：**已确定**（客户拍板）。
- **背景**：客户主动复盘提问"app 已在运行时，你会不会做隔离编译、增大项目目录"。
  实测证实该推测成立：
  - Windows 锁住运行中的 exe → `cargo build` 无法覆写 `target/debug/mf-perch.exe`
    （`os error 5` / `32`）；当时的处置是把 `CARGO_TARGET_DIR` 指向
    `src-tauri/target-verify` 旁路验证；
  - 代价从未被量化过：实测该目录 **7.9 GB / 5803 个文件**，相当于主 `target`
    的 72%（主 `target` 同口径 `du -sh` 为 **11 GB**，2026-09-18 实测；
    与 `development-troubleshooting.md` 中 2026-09-16 用 `Get-ChildItem` 统计的
    12.33 GB 属**不同工具、不同日期**的两个读数，非矛盾，口径以 `du -sh` 为准）
    ——即主缓存的 72% 被重复了一份，且 app 关闭后即**永久失去价值、无人回收**；
  - 该做法只留在 `.gitignore` 的一条注释里（`src-tauri/target-*/`），
    `AGENTS.md` 与设计文档均未记录——**做过但没沉淀**，既不会被复用也不会被清理。
- **决策（客户原话："正确的做法是一条直线"）**：
  1. **禁止**为解决"文件被锁 / 端口被占 / 实例冲突"这类环境障碍而开辟第二条构建直线
     （备用 target 目录、备用端口、备用路径等）；
  2. 遇阻**停下来向客户求助**，客户会**退出正在运行的 app 实例**来腾出构建条件；
     属残留 / 孤儿进程时先跑 `pnpm dev:clean`，仍清不掉就把进程名与 PID 报给客户；
  3. 例外必须在**事前**取得客户同意，且**用后即删**、同步登记进文档——三者缺一即不成立。
- **影响**：
  1. **磁盘**：`src-tauri/target-verify/` 删除，回收 7.9 GB；
  2. **`.gitignore`**：`src-tauri/target-*/` 的忽略规则**保留**（防止将来误入库），
     但注释口径改为"不应产生的遗留目录"，不再把它描述成一种可选处置；
  3. **原则**：新增 [`docs/design/principles.md`](../design/principles.md) **P4**
     （遇到障碍求助，不得用绕过手段维持推进）——上升为通用工程原则，
     不只约束构建这一处；
  4. **AGENTS.md**：§5.11 的纪律由三条增为四条，让接手的 Agent 在**必读文件**里就能看到，
     不必先发现 troubleshooting 里那一节；
  5. **过程记录**：`docs/development-troubleshooting.md` 新增对应条目（现象 / 旧处置为何错 /
     正确做法 / 预防）。
- **顺带修正的文档事实**：`development-troubleshooting.md` 中 E0463 一节原写
  "`target` 约 40 GB"，与同文档实测的 12.33 GB 及本次 `du -sh` 的 11 GB 矛盾，
  已按 2026-09-18 实测值统一（同一文档内两处数字不一致会误导接手者评估 `cargo clean` 的代价）。
- **测试**：无新增测试。本条是**流程约束**，不产生可断言的代码行为；
  其落实靠文档与 §5.11 纪律，而非测试（§5.1 自检："失败时指向用户会在意的问题吗"——答否，故不写）。

  `docs/development-troubleshooting.md`。
