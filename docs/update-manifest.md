# 更新检查：update.json 清单格式

> 对应决策 D23 / D42 / D55 / D58，问题 Q21 / Q34。
> 应用从**可配置的 URL** 读取一个 JSON 版本清单，发现新版本时提示用户去该版本的发布页下载。
> 默认源与"随发布自动更新"的机制是 **D55**（开源化后取代 D23 的 Gist 方案第 2 点）。

---

## 1. 默认源与维护方式

应用**内置了默认更新源**（D42），开箱即可检查更新，用户无需填写任何地址：

```
https://raw.githubusercontent.com/mangfu26/mf-perch/main/update.json
```

- 清单文件是仓库根目录的 **`update.json`**，由**发布流水线在每次发版时自动生成并回写
  main**（**D55**，见 `.github/workflows/release.yml` 的 "Publish update manifest to main"）——
  维护者**不需要也不应该手工编辑它**；
- 地址用**分支名 `main` 而非固定 commit SHA**：pin 在 SHA 上意味着每次发版都要改内置地址，
  等于没有更新机制；`main` 的 raw 内容随合入即时变化；
- 设置页「更新源地址」默认显示内置地址，可被用户覆盖，并有「恢复默认」按钮。

---

## 2. 清单格式

`update.json` 的完整结构与字段含义如下（示例见
[`update-manifest.example.json`](update-manifest.example.json)，格式与该文件一致）：

```json
{
  "version": "0.2.0",
  "release_url": "https://github.com/mangfu26/mf-perch/releases/tag/v0.2.0",
  "notes": "本次更新内容，支持多行。",
  "pub_date": "2026-09-15T10:00:00Z",
  "platforms": {
    "windows-x86_64": {
      "url": "https://github.com/mangfu26/mf-perch/releases/download/v0.2.0/mf-perch_0.2.0_x64.msi",
      "sha256": "安装包的 SHA256（供用户核对）",
      "size": 12345678
    }
  }
}
```

### 字段说明

| 字段 | 必填 | 说明 |
| ---- | ---- | ---- |
| `version` | ✅ | 最新版本号。语义化版本，允许带 `v` 前缀（如 `v0.2.0`） |
| `release_url` | —（流水线一定写） | **该版本的 Release 页面**地址，即界面上「前往发布页下载」按钮的目标（**D58**）。缺失时应用从 `platforms.<键>.url` 推导同一个 tag 的发布页（`…/releases/download/<tag>/<文件>` → `…/releases/tag/<tag>`），推导不出才没有按钮 |
| `notes` | — | 更新说明，界面会原样展示（支持 `\n` 换行）。发布流水线取 CHANGELOG 对应小节 |
| `pub_date` | — | 发布时间（RFC3339） |
| `platforms` | — | 各平台安装包；键名为平台标识 |
| `platforms.<键>.url` | ✅（若提供该平台） | 安装包直链。**不是给用户点的地址**（D58），只用于标识本平台那个包、以及在上表 `release_url` 缺失时推导发布页 |
| `platforms.<键>.sha256` | — | 安装包 SHA256，界面会展示供用户核对 |
| `platforms.<键>.size` | — | 文件大小（字节） |

### 平台标识

当前版本使用 `windows-x86_64`。将来支持其他平台时，对应的键为：

| 平台 | 键名 |
| ---- | ---- |
| Windows x64 | `windows-x86_64` |
| Windows ARM64 | `windows-aarch64` |
| macOS Apple Silicon | `darwin-aarch64` |
| macOS Intel | `darwin-x86_64` |
| Linux x64 | `linux-x86_64` |

### 为什么按钮指向发布页而不是安装包（D58）

- 同一个 Release 下并列着多种安装包（Windows 就有 msi 与 setup.exe 之分），
  直链等于**替用户挑了格式**；将来多平台时还要替用户挑平台；
- 清单缺当前平台条目时（含平台标识为 `unknown` 的机器），直链会退化成
  "有新版本却没有入口"。发布页与平台无关，永远点得开。

`platforms` 中缺少当前平台的条目时，应用**仍会提示有新版本**，
并且只要 `release_url` 在（或能从直链推导），下载按钮照样可点；
两者都没有时界面才退回"请到仓库 Releases 列表自行查找"的提示文字。

## 3. 更新时的行为

| 情况 | 应用表现 |
| ---- | ---- |
| 远端版本 **高于** 本地 | 提示新版本，展示更新说明与「前往发布页下载」按钮（**D58**：指向该版本的 Release 页面） |
| 远端版本 **等于** 本地 | 提示"已是最新版本" |
| 远端版本 **低于** 本地 | 判为最新——**不会提示降级**（避免开发版被诱导降级） |
| 版本号无法解析 | 判为检查失败并给出原因，**不会误报有新版本** |
| 用户点了「忽略此版本」 | 该版本不再提示；出现更新的版本时会重新提示 |
| 网络不通 / 地址错误 | 自动检查**静默失败**（不打扰用户）；手动检查会明确告知原因 |

**不会自动下载或安装**：只提示，由用户点击按钮在系统浏览器中打开该版本的发布页，
自己挑平台与安装包格式。

---

## 4. 注意事项

- **`version` 不带 `v` 前缀**（流水线从 tag 去掉 `v` 后写入，人工修订单也不要加）：
  解析容忍 `v`，但"忽略此版本"是字符串精确比对，带前缀会对不上；
- **`sha256` / `size` 不要填占位文字**：它们会原样展示给用户核对，
  填"待补充"这类文字等于给用户看假校验值——**要么填真实值，要么整个字段删掉**（两者都可选）。
  流水线取的是真实构建产物的哈希与字节数，不存在占位问题；
- **首发时清单版本应等于应用版本**（如都是 `0.1.0`），否则所有用户一装上就被提示更新，
  而对应的 Release 可能还不存在；
- **发版顺序由流水线保证**：先建 Release（下载地址可用），再回写 `update.json`，
  顺序反了会把用户引导到不存在的页面——不要绕过流水线手工改 `update.json`；
- **检查频率**：自动检查有 24 小时缓存，不会每次启动都请求。
- **关闭自动检查**：用设置页的「启动时自动检查更新」开关；
  把更新源清空只是回退到**内置默认地址**，不等于关闭检查（D42）。

## 5. 发版清单（人工部分只有两步）

D55 之后，`update.json` 的 `version` / `release_url` / `url` / `sha256` / `size` 全部由**发布流水线**
从真实 tag 与真实构建产物生成并回写 main（**D54** 的流水线，"Publish update manifest to
main" 步骤），"忘记更新版本信息""文件名抄错导致 404"这类故障已从机制上消除。人工只剩：

| # | 事项 | 说明 |
| ---- | ---- | ---- |
| 1 | 在 `CHANGELOG.md` 补写本版小节（`## [vX.Y.Z] - 日期` + 变更内容） | Release 正文与清单 `notes` 都取自这里；**缺小节流水线直接失败** |
| 2 | 同步 `src-tauri/tauri.conf.json` 的 `version` 后，在 main 上打 tag `vX.Y.Z` 并推送 | tag 与应用版本的一致性由流水线校验（**D54**），不一致会红灯 |

验证方式：Release 创建成功、main 上出现 `chore(release): …` 回写提交后，
用应用手动「检查更新」确认能读到新版本即可。
