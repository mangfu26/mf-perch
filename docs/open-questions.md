## 已确认结论

### Q1 — 目标 MCP 客户端与传输方式

- 客户答复：不限定具体客户端，"都有可能"，应用只需遵循标准 MCP 规范即可。
- **补充答复：只支持 Streamable HTTP 即可，不支持 stdio。** 理由：现有工具可将 Streamable HTTP 转换为 stdio，不支持 Streamable HTTP 的客户端可通过转换工具接入。
- 结论：**传输层只实现 MCP Streamable HTTP**，不做 stdio 传输，也不做 stdio 桥接进程。
- 附带约束：MCP Server **必须使用官方 Rust SDK**（[`rmcp`](https://github.com/modelcontextprotocol/rust-sdk)）开发。
- 架构师核实（2026-09-09，rmcp 3.2.0）：
  - 服务端 Streamable HTTP 传输：feature `transport-streamable-http-server`（本次采用的唯一传输）
  - 服务端 stdio 传输（`transport-io`）本次不使用
  - `rmcp` 3.2.0 不含 SSE 传输 feature；若后续需兼容仅支持旧版 HTTP+SSE 的客户端，需另行评估

### Q2 — MCP 端点暴露与鉴权

- 客户答复：
  1. **默认只监听 `127.0.0.1`，但支持用户开放远程连接**（因为 Agent 可能运行在与本应用不同的主机上）。
  2. **接受"自动生成 Token + 手动复制到客户端"流程。**
  3. **端口策略（三步走）**：
     - 首次安装启动，默认尝试 `50001`；被占用则依次 `50002`、`50003` …… 直到找到可用端口；
     - 首次启动成功后，**将第一个成功监听的端口持久化**，作为下次启动的默认端口；
     - 下次启动时若该持久化端口被占用，**重新从 `50001` 开始迭代**寻找可用端口，启动后再次持久化记录。
- 结论：
  - 监听地址：默认 `127.0.0.1`；提供"允许远程连接"开关，开启后监听 `0.0.0.0`。
  - 鉴权：应用自动生成随机 Token（Bearer），设置页可查看/复制/重置。
  - 端口：按上述三步走策略实现，端口号持久化在本地配置中。
- 架构师风险提示（已登记为 Q30）：开启远程连接后，流量将离开本机回环，仅有 Bearer Token 不足以保证传输安全，需评估是否强制 TLS、是否限制来源 IP。**默认关闭远程连接**，并在开启时给出安全警告。
- **后续（Q30 已答，2026-09-10）**：客户决定**暂不支持 TLS**，接受局域网内的残余风险，保留为未来工作。
  现有措施：Token 鉴权（常量时间比较）+ 默认仅监听回环 + 开启远程时界面风险告警。
  详见 [`decisions.md`](decisions.md) 的 D30。

### Q3 — 终端会话模型

- 客户答复：**同意方案 C**，按设计文档执行。
- 结论（详见 [`docs/design/terminal-session.md`](design/terminal-session.md)）：
  - 终端 = 常驻 SSH 会话（保留 cwd / 环境变量 / 同进程内 `export` 等状态），**不申请 PTY**。
  - 命令传输采用 **NUL 字节分帧**（`命令内容 + \x00`），**不依赖 base64 等任何外部命令**；远端用 bash 内建 `read -r -d ''` 读取。
  - 命令结束由脚本自打印的 `__MF_PERCH_END__<nonce>__<seq>__<rc>__` 标记判定，nonce 每会话随机，防误判。
  - **不支持 `vim` / `top` / `less` 等交互式全屏程序**（无 PTY 的必然结果）。
  - **远端必须存在 bash**；创建终端时探测 `command -v bash`，缺失则返回明确错误。
  - 单条命令卡死时 MVP 终止整条会话，终端置为 broken，由 Agent 重建；精细 kill 放二期。
- 环境变量策略（客户已同意）：
  - 默认以 **`bash -l -c`（S2 登录 shell）** 启动，加载 `/etc/profile` 与 `~/.bash_profile`，使 Agent 环境接近人类 SSH 登录。
  - 提供**每主机可选的初始化脚本**（S3），用于 nvm / conda 等特殊环境。
  - 提供**每主机可切回干净模式**（S1）的开关。
  - 创建终端时捕获环境快照（PATH / PWD / bash 版本）存入终端元数据。
  - **READY 标记之前的输出一律丢弃**，隔离 profile 欢迎语等噪声。

### Q4 — 命令执行时序模型

- 客户方案：同步 + 异步双模式并存，由 Agent 自行判断选择。
- 客户答复：**1 采纳、2 可以、3 选 A（排队）**。
- 结论（详见 [`docs/design/command-execution.md`](design/command-execution.md)）：
  - 工具集合：`run_command`（同步）/ `run_command_async`（异步）/ `get_command_status`（轮询）。
  - **同步超时降级为异步**：超时返回 `command_id` + `status=running`，不报错、不中断远端命令。这是避免模型误判耗时后重试、造成命令重复执行的关键。
  - 同步默认等待 30 秒、上限 50 秒。
  - **同一终端串行**；终端忙时**排队**（A），队列上限 10 条，超出拒绝。
  - 状态取值：`queued` / `running` / `completed` / `failed` / `broken`。
  - 跨终端可并行；人类界面通过 Tauri 事件实时流式查看输出。
  - 输出上限（建议默认 1 MB / 20000 行）超出时截断并标注 `truncated`。

### Q5 — 凭据与数据存储

- 客户答复：**所有数据存放在同一个 SQLite 数据库**（便于后续备份与同步，单文件迁移即可）；**SSH 密码与 SSH Key 加密后存储**，不落明文。
- 结论（详见 [`docs/design/credential-storage.md`](design/credential-storage.md)）：
  - 单文件 SQLite 存放主机、认证信息、终端、命令历史。
  - **字段级加密**（AES-256-GCM 或 XChaCha20-Poly1305）：密码、私钥、passphrase 加密；主机地址、名称、用户名、命令历史等元数据明文。
  - **加密主密钥必须存放在数据库之外**（否则拿到库文件即可解密），具体方式见 Q31。
  - 明文凭据仅短暂存在于内存，用后 `zeroize`；凭据绝不通过 MCP 返回；日志禁止输出凭据。
- 架构师提示（登记为 Q31）：密钥管理是核心决策点，建议系统钥匙串。

### Q6 — 首发平台

- 客户答复：**首发仅 Windows**；但**必须遵循跨平台架构**，以便成熟后提供 macOS / Linux 桌面版支持。
- 结论：
  - 首发仅构建与测试 Windows 版本。
  - 架构上**不写死平台特定代码**：平台相关能力（密钥存储、数据目录、托盘行为、通知）统一抽象为 trait/接口，按平台提供实现。
  - CI 首发只跑 Windows 构建；跨平台构建留待二期启用。
  - 设计评审时需检查是否存在平台耦合（如硬编码路径、直接调用 Windows API）。

### Q7 — SSH 库选型

- 客户答复：**使用 `russh`**。
- 结论：SSH 客户端实现采用 `russh`（纯 Rust、基于 Tokio 异步、无 C 依赖）。
- 理由：跨平台打包干净（无 native 依赖），与 Tokio 异步运行时契合，支持密码 / 公钥认证与 ProxyJump 等所需能力。
- 版本核实（已完成）：实际采用 `russh 0.63`，`default-features = false`，
  启用 `flate2` / `ring` / `rsa`。**刻意用 `ring` 而非默认 `aws-lc-rs`**，
  因为后者需要 cmake + nasm，会让多数开发机与 CI 构建失败（见 D9）。
- **⚠️ 未完成项（2026-09-10 核实）**：**ProxyJump 整体未交付**，尽管 D11 / Q9 明确"MVP 含 ProxyJump"。
  实际状态（只做了管道，没有功能）：
  - ✅ 数据库列 `proxy_jump_host_id`、领域模型字段、`hosts` 读写、IPC 入参/出参均已存在；
  - ⚠️ 前端 `HostFormDialog.vue` **没有渲染选择跳板机的控件**（表单仅把该字段默认置 `null`）；
    `i18n` 里的 `proxyJump` / `proxyJumpNone` 词条**未被任何组件引用**；`api.ts` 仅有类型声明；
  - ❌ **连接层完全未使用**：`ssh::session::Session::connect` 直接连接
    `(host.address, host.port)`，没有任何跳板逻辑。

  即：**目前没有任何路径能让 ProxyJump 生效**，属已承诺但未实现的功能，需补齐
  （连接层 + 界面控件 + e2e）。在补齐前，不要在任何对外说明中声称支持 ProxyJump。

### Q8 — 主机密钥校验策略

- 客户答复：**接受，采用 S1（TOFU）**。
- 结论：
  - 首次连接主机时记录其主机密钥（存入本地数据库）。
  - 后续连接比对：一致则正常连接；**不一致则红色告警并阻止连接**，需人类显式确认后方可更新。
  - MVP **不实现** S2 严格模式（客户未要求），但接口上预留策略字段，便于二期扩展。

### Q9 — MVP 的 SSH 高级能力范围

- 客户答复：**同意只做 ProxyJump**；但补充了 sudo 密码处理的建议（见 Q33）。
- 结论：
  - **MVP 含 ProxyJump**（连内网主机是核心链路必要条件）。
  - **SFTP、端口转发进二期**。
  - **sudo 提权**按 Q33 的三模式设计推进，**一期全部实现**（客户决定）。

### Q33 — sudo 提权三模式

- 客户答复：**采纳三模式设计，一期（MVP）全部实现**。
- 结论（详见 [`docs/design/sudo.md`](design/sudo.md)）：
  - 每主机可配策略：`deny`（默认）/ `ask` / `auto`。
  - 透明拦截：包装脚本中定义并 `export -f sudo() { command sudo -A -p '' "$@"; }`。
  - 密码投递：askpass 脚本 + 远端 FIFO（`~/.mf-perch/sudopw.fifo`），应用经独立 SSH channel 写入；**不落盘、不进环境变量**。
  - `ask` 模式经系统通知征求用户同意，拒绝或 60 秒超时则关闭 FIFO 使 sudo 失败。
  - fail-closed：未被拦截的 sudo 调用一律失败，不静默提权。
  - 会话建立时先探测 `sudo -n true`，已配免密 sudo 则无需注入。

### Q10 — SSH 私钥导入

- 客户答复：
  - 导入方式：**文件选择器 + 粘贴文本**（两种都支持）。
  - 格式：**OpenSSH + PEM，不含 PPK**。
  - **支持 passphrase**。
  - 界面**只显示指纹**，不显示私钥正文。
- 结论：
  - UI 提供"选择文件"与"粘贴文本"两个入口。
  - 解析支持 `-----BEGIN OPENSSH PRIVATE KEY-----` 与 PEM 格式；PPK 明确不支持，导入时给出友好错误。
  - passphrase 加密存储（复用 D6 字段级加密），连接时用于解锁私钥。
  - 导入后界面仅展示指纹（如 SHA256）与格式，正文不回显。

### Q11 — 终端数量与并发上限

- 客户答复：
  1. 每主机 **5** 个、全局 **20** 个，**均可配置**。
  2. 超限**拒绝**，不自动归档，由 Agent 自行决定是否归档。
  3. **归档终端不占配额**。
- 结论：
  - 创建终端时校验两级配额（每主机 / 全局），仅统计**活跃（未归档）**终端。
  - 超限返回明确错误，提示已达上限并建议归档不用的终端。
  - 上限值在设置页可调整。

### Q12 — 命令历史保留策略

- 客户答复：**1 采纳、2 同意（不要分钟级、不要立即清空）、3 归档终端永久保留**。
- 结论（详见 [`docs/design/history-retention.md`](design/history-retention.md)）：
  - **按时间保留**：默认 30 天，可配置 1 小时 ~ 永久，单位 小时/天/周/月。
  - **不设条数上限**（高危操作必须完整保存，不因条数自动删除）。
  - **不支持分钟级保留期**，**不提供"立即清空"按钮**；磁盘紧张时由用户手动删除归档终端释放空间。
  - **归档终端历史豁免保留期，永久保留**，直到用户手动删除该终端（客户已明确确认：期限只约束活跃的未归档终端）。
  - 保留期实际作用于**活跃终端**的历史；每 24 小时 + 启动时清理一次，清理行为留痕。
  - 数据位置：应用数据目录下单一 SQLite（D6）。

### Q13 — 前端技术栈

- 客户答复：**可以**（客户更熟悉 Vue，采纳切换建议）。
- 结论（详见 [`docs/design/frontend-stack.md`](design/frontend-stack.md)）：Vue 3（`<script setup>` + Composition API）+ TypeScript + Vite + Tailwind CSS + shadcn-vue + Pinia + Vue Router + xterm.js + lucide-vue-next。

### Q14 — 应用形态

- 客户答复：**采用 A（关闭窗口最小化到托盘）**。理由：本应用实质是为 AI Agent 提供终端访问代理，关窗即退出会严重影响体验。
- 结论：
  - 关闭窗口 → **最小化到系统托盘**，应用与 MCP Server 持续运行。
  - **托盘图标常驻**，右键菜单含"打开主界面"与"退出"。
  - 真正退出需经托盘菜单或应用内菜单；**退出前若有活跃终端，给出确认提示**。
  - **开机自启不做**（二期），设置页预留开关位置。

### Q15 — 使用模型

- 客户答复：**A（单机单用户）**。
- 结论：
  - 不做账户体系、不做登录、不做权限分级、不做多租户隔离。

### Q16 — 界面语言与 i18n

### Q17 — 命令历史审计能力

- 客户答复：**首发做"时间线 + 全文搜索 + 筛选"即可**。
- 结论：
  - **MVP 能力**：
    - 时间线查看（命令、输出、退出码、耗时，按时间排序）；
    - 全文搜索（命令与输出内容，基于 SQLite **FTS5**）；
    - 按终端 / 主机筛选。
  - **导出（CSV / JSON / 文本）放二期**。

### Q18 — 归档终端的恢复

- 客户答复：**① 允许人类恢复；② 恢复后延续原终端 ID 与历史**。
- 结论：
  - 人类在终端详情页可执行"恢复归档"操作，终端重新对 Agent 可见。
  - **恢复沿用原终端 ID**，命令历史连续，不新建终端。
  - 归档时 SSH 会话已关闭，因此恢复会**重建底层会话**（新 SSH 连接 + 新包装脚本），但终端实体与历史延续。
  - 恢复操作需记入审计（谁在何时恢复了哪个终端）。
  - 配额校验：恢复前需检查是否超出终端配额（Q11）。

### Q19 — 删除终端时历史一并删除

- 客户答复：**确认采用 A**。
- 结论：
  - 人类删除终端 = 删除该终端及其**全部命令历史**，不可恢复。
  - 需**二次确认**，弹窗明确告知"历史将一并删除且不可恢复"。
  - 与 Q12 一致：用户可通过删除归档终端**释放磁盘空间**（历史不保留，空间才真正释放）。
  - 不产生"无主历史"记录。

### Q20 — 长命令完成的通知

- 客户答复：**A（MVP 仅应用内状态更新）**。

### Q21 / Q34 — 更新检查与版本源

- 客户答复：**采用 Gist 作为版本信息源**，接受人工同步 Gist 的风险（因为发布流程本身由客户掌控）。
- 客户说明的发布流程：
  1. 客户指示团队给 `main` 打 tag（或客户手动打）；
  2. 推送到 GitHub；
  3. GitHub Actions 检测 tag → 构建产物 → 创建 **Release 草稿**（是否发布由客户决定）；
  4. **客户手动更新 Gist**。
- 结论（详见 [`docs/design/update-check.md`](design/update-check.md)）：
  - 版本源：**Gist 托管的 JSON 版本信息**；**更新源 URL 可配置**（便于换源/镜像）。
  - 启动后台检查 + 设置页手动检查；发现新版本提示并跳转下载。
  - 异步静默失败、24h 缓存、semver 比对、忽略此版本、可关闭自动检查、不自动打开浏览器、显示 SHA256。
  - **不做自动下载与自动安装**。
- **红线（写入决策记录）**：团队不得在客户未明确指示时创建或推送 tag；不得自动合并到 `main`。

### Q26 — 测试环境

- 客户答复：本机 Windows 10，**使用 WSL 测试**；客户已安装 WSL Ubuntu 26.04。
- 结论（详见 [`docs/design/test-environment.md`](design/test-environment.md)）：
  - 已搭建：openssh-server 监听 `127.0.0.1:2222`、测试用户 `mfperch`（有 sudo 密码）、免密用户 `mfperch-nopass`、测试密钥对、profile 标记与测试 PATH 目录。
